## 3. 根因审查：事实、解释和待验证项

### 3.1 F2：下一目标非法，插入动作并未发生

[DIAGNOSIS_001.json](实现审计/goal_pilot48_v1/f2_inside_preinsert_failure_review_v1/DIAGNOSIS_001.json)记录：搬运step1367–1753成功，随后 `preinsert_30mm` 为 `IK_FAIL`，执行起止step均为null；新目标相对实际EEF约平移(+0.1858,−0.00035,−0.2341)m并旋转179.793°。原生手部几何检查发现掌部/桌面、掌部/盒体及手指/盒体相交；去buffer的诊断也未消除交叠。

审查结论：这个特定目标/抓法/容器组合存在已记录的必要条件失败；继续换seed或搬运hub不能修复终点几何。有限IK失败不是所有F2任务数学不可行的证明。本轮未观看F2完整视频，也未重跑几何脚本；停止位置与交叠结论来自已保存机器诊断。

[larger-box影响说明](实现审计/goal_pilot48_v1/f2_larger_box_design_v1/IMPACT.md)已明确新尺寸意味着新布局。其闭手插入必要条件可复用为分析方法，但未证明实际打开、退出、支撑、全臂路径或新三分支成功；约1.1447倍不能直接作为新模板的最终尺寸。

### 3.2 F3：支撑下稳定，离台保持持续失稳

[post-lift报告](实现审计/goal_pilot48_v1/f3_postlift_terminal_review_v1/REPORT.md)记录lift row1409–1518实际执行，最后pad接触在1412；确认窗1519–1568无pad/table接触，双指持续接触，但最终相对漂移6.064509mm/0.057581rad，超过原5mm/0.05rad。确认窗rise从22.359669降至20.396054mm，49个相邻差均为负。

因此不能把“有双指接触”“抬升终点尚在阈值内”“actor最终仍升高20mm”单独作为通过。也不能将不同失败尝试分别通过的子门拼成成功。已确定的近因是承重后的相对位姿不能保持；接触几何、动力学参数和控制分别贡献多少，尚未有因果隔离证据。

### 3.3 质量—惯量：优先排查，尚未完成运行时归因

[旧design_spec](实现审计/goal_pilot48_v1/f3_upright_design_v1/design_spec.json)及其引用的 `Robotwin2/datasets/p48_f3_one_sided_micro_001/actual_mass_properties.json`记录mass≈0.01kg、principal inertia≈[0.002876115,0.000345467,0.002881626]kg·m²。分享页按同源包络/COM估算任意轴上界mR²≈0.000212kg·m²，两个主惯量约为其13.6倍。

这个上界计算的前提是几何、COM、质量和惯量对应同一刚体、同一尺寸与单位。新执行先独立复算这些条件；本轮只核到了记录数值，未重新构建刚体或独立计算13.6倍。

本轮直接读到官方源码 `Robotwin2/project/RoboTwin/envs/utils/actor_utils.py`：`Actor.__init__(mass=0.01)`调用`set_mass`，后者只设置`component.mass`。这是强解释线索；PhysX文档也说明设置mass不自动更新惯量，但安装版SAPIEN的包装前/后实测仍必须做，不能用文档代替运行时证据。[PhysX PxRigidBody](https://nvidia-omniverse.github.io/PhysX/physx/5.1.3/_build/physx/latest/class_px_rigid_body.html)

### 3.4 材料与尺寸：两个独立的数据来源问题

[材料审查](实现审计/goal_pilot48_v1/f3_material_baseline_review_v1/IMPACT.md)区分场景声明0.5/0.5与mesh loader默认约0.3/0.3、restitution0.1。上次失败场景未在断言前逐shape保存实际值，因此不能补造该场景材料表。新factory必须先保存，再校验。

本轮新增源码发现：`create_actor.py:create_actor`成功读取metadata后执行`scale=model_data["scale"]`，可能覆盖调用参数；mesh collision调用未显式传入场景material。故新设计不能只传一个scale就声称改了尺寸，不能用scene属性冒充shape实际材料。

## 6. 工作包 W1：资产物理与操作几何基线

### 6.1 质量属性读取与一致修复

每个主对象记录四个阶段：native body构造后/Actor包装前；包装后；任何质量/scale修订后；settle后。保存actor/shape身份、最终native尺寸、scale/各坐标变换、mass、COM平移及质量主轴姿态、principal inertia、每shape实际材料、密度来源、gravity/kinematic标志和动态体类型。

先用几何顶点变换到同一actor坐标，与COM求R；校验单位m/kg/kg·m²、有限正值、惯量三角不等式及I≤mR²。上界通过只是必要条件，不代表物性真实。几何与质量分布还须有明确来源。

同一几何和相同归一化质量分布下可用I1=I0·m1/m0，保留正确COM及主轴；几何尺寸改变则先按最终几何重新构建，不能套用单纯质量缩放。非均匀缩放、不封闭网格、空腔与多shape重叠须明确建模假设，避免体积重复计数。10g是否保留应由新物性规格说明，不能仅因为旧默认值是10g就视其为物理真值，也不能为了抓得住反复减重。

安装版已有`ActorBuilder.set_mass_and_inertia`接口线索，可核其源码后采用；选择哪条实际接口由版本测试决定。设置后再次readback，防Actor包装再次覆盖。SAPIEN对构造与质量属性提供分开的接口。[SAPIEN ActorBuilder源码文档](https://sapien-sim.github.io/docs/_modules/sapien/wrapper/actor_builder.html)

## 7. 工作包 W2-F2：最小完整 inside 操作

### 7.1 设计与备选顺序

优先对一个明确的现有宽口平底盒做完整包络筛选；若复杂底面或张开/退出空间成为障碍，进入预先声明的5片参数化盒备选。不对一串未知资产跑无界搜索。冻结候选选择依据及失败资产记录。

闭手插入、开手、退出三种姿态都需合法。尺寸计算应联合考虑罐体完整内含、盒顶原余量、侧壁原余量、手掌高度、指尖闭合/展开扫掠、实际contact offset、配置碰撞buffer和跟踪误差。误差余量来自已有实测/明确工程规则，不凭空填毫米数，也不把加大盒子误写为放宽成功门。

若要求罐体全部低于盒沿，而侧夹位置导致手掌/指根被盒壁阻挡，应报告该组合冲突并重选盒形/抓取位置；仅增宽未必解决高度冲突。盒子可达、台面支撑、与scale/stand/干扰物互不冲突必须一起满足。

### 7.2 目标与接触状态机

在实际稳定抓持后测`T_EEF_can`，使用`T_world_EEF*=T_world_can* inverse(T_EEF_can)`推导目标；每段计划固定该抓持证据，执行中监测漂移，不能逐帧重设基线掩盖滑移。禁止照搬旧saved_contact姿态、box__9或gravity-drop路线。

顺序：抓起 → 共同中间位姿 → 盒口上方 → 保持罐姿态竖直下降 → 实际底板支撑确认 → 慢开 → 物体与夹爪解除关系 → 空手垂直退出 → rest/settle → 独立终态verifier。

| 阶段 | 物理/规划一致性要求 |
| --- | --- |
| carry/preinsert | 不允许提前借最终floor支持规则放行；机器人、侧壁、设施碰撞完整检查 |
| 最后受控下降和闭爪支撑确认 | 只允许准确底板role/shape、真实接触、无穿透、持续抓持条件同时成立的物体—底板pair |
| 慢开 | 不用原闭爪刚性attachment假设代替真实物体状态；记录每步开度/接触/支撑 |
| detach/退出 | 先证明物体受支撑及gripper脱离，再撤attached model并把物体按真实位姿写回world；不得全局隐藏罐子/容器 |
| rest/终态 | 罐体稳定在inside region；on/beside竞争region为false；手部退出、无重新接触和超阈值干扰物移动 |

按分享方案，本计划建议以已有50帧支撑、慢开、250帧settle、最终50窗/EEF速度作新设计的待审验收基线，逐项核适用性并绑定新verifier版本；这是明确选择的技术提案，不是自动继承旧Goal。不把“5mm底面内缩”恢复为要求物体悬空，也不移除侧面/顶部原5mm界限。新floor几何必须独立绑定，不把旧shape白名单复制过去。

### 7.3 成功和确认

## 8. 工作包 W2-F3：自然竖立、对称侧夹和带载闭环

安全工作高度从实际夹持几何计算：设中心参考点高度为z_c，夹持总成相对参考点最低偏移为d_min，V负向最大位移为A_V，最高禁止支撑面为z_s，净空为c，则必须满足 `z_c − A_V + d_min ≥ z_s + c`。同时检查正V、左右H、全臂与相邻设施的扫掠。原约55mm V幅度不能在仅25mm离台后直接执行；若全臂工作区不允许，改布局/抓取几何，不能无审查减幅或改轴。

V、H各为从中心出发经正负方向并返回中心的一整个闭环，固定table-frame `±z_table`与`±x_table`，不是单向位移或瓶体竖/横姿态。事件必须由隐藏realized EEF/瓶体轨迹、抓持连续性、幅度、偏轴和闭环返回证明，不由command名称宣布。

## 10. 多GPU并行执行合同（用户本轮明确要求）

新合同/manifest/调度器必须使用`allowed_physical_gpu_indices=[0,1,2,3,4,5,6,7]`，允许独立fresh-idle卡并行，理论上限8；实际并发数由已ready独立作业、空闲卡、总余额和CPU/RAM/缓存资源共同限制。初期通常只有F2与F3两条ready链，不为占满卡而启动重复尝试。

这项最新要求覆盖旧`CONTRACT.json:max_concurrent_GPUs=1`、`gpu_jobs_serial=True`和分享页“GPU串行”。旧合同与旧回执仅历史保留；新建独立多卡合同和运行层，不将旧Goal合同作为父合同。本轮不修改旧运行合同。不得让某层仍拒绝GPU1–7时静默退回GPU0。

具体要求：

1. 每wave取得GPU0–7完整实测snapshot；每个job在launch瞬间再次由Guard原子检查并UUID绑定。近baseline显存、低利用率、合理P-state、无compute进程且无他人活动才可用；snapshot不等于占卡reservation。
2. 每卡最多一项目job，root固定一卡。无空闲则不launch；一张可用就启动一条，不等两张/八张同时空闲。外部进程不触碰、不停、不抢。
3. 每job独立scene/planner进程、缓存/tmp、输出目录和CPU线程限额。共享只读源码/资产可复用，编译缓存预构建或加锁，运行中不得修改被hash绑定的源码；TMP路径保持短且在workspace内。
4. 总账只有一个协调者写：各worker只写私有meter/receipt，协调者在事务锁内计算`cap-used-reserved`、预留有限上界、签发唯一job_id。旧预算模块明确拒绝第二个活动reservation，必须新版本移除单作业假设并保留总额/重复ID保护。
5. `STATE.running`单值改为新版本的job映射，不允许一个job清理时把其他running清空；ledger/STATE/pilot索引/hash链发布顺序及崩溃恢复须审查。旧ledger只读存档；新任务以独立获批cap和零新消耗开始自己的hash链，不carry-forward旧余额。新任务各GPU共享这一份新账本，不能分别拿一份预算。
6. 终态按job幂等对账，释放自己的预留与设备lease；预算GPU时间是各job耗用的和，多卡壁钟缩短不产生免费GPU秒。计数未知时停止新派发，保留在途job证据并按任务所有权安全收尾。
7. CPU回归先验证并发抢同一卡、同时预留导致超额、重复终态、乱序完成、协调者在append后/STATE更新前崩溃、NFS锁可见性、忙卡未启动0消耗及非零卡映射。假Guard可验证逻辑；真实Guard并发集成验证并入已批准的两族首个小作业，不另开无界测试波次。
8. 子进程使用项目环境：unset继承的LD_LIBRARY_PATH、CUDA_VISIBLE_DEVICES绑定选中UUID、CUDA工具链`Robotwin2/tools/cuda-12.1`；渲染器也需证明实际device绑定，没有在别卡隐式分配。
9. timeout/失败/取消均追踪PID、PPID、PGID、启动时间与worker树，清理并reap自己启动的进程；宿主机上下文复核，不能以沙箱ps不可见当作退出。post snapshot确认无任务compute且卡回baseline，原始失败不倒写。若外部作业抢入导致无法观测baseline，保留原post失败、记录owned清理证据并等待追加释放复核，不杀外部作业或先报完成。

物理失败通常只阻断本族依赖链，另一独立族可继续；source/账本完整性、所有权不明或资源计数未知是全局停止新派发条件。多卡本身不授权多agent，本计划由一个协调者管理GPU工作进程即可。
