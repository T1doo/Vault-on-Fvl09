# 二、第一项关键缺口：批量场景还不够具体，部分设计与正式规范冲突

## 1. 当前 56 个槽位主要只是整体微移

生成器给各场景设置的主要参数是：

```text
整体 X 平移：2 mm、4 mm……28 mm
整体 Y 平移：−1 mm、0、1 mm
尺寸倍数：固定为 1
appearance_rotation：0/1/2
预期投影间距比例：按难度填入
```

这适合作为**检查流水线是否能处理不同参数的低风险候选**，但还不是一套已经落实的正式场景多样性方案。生成器里没有具体列出每个干扰物、设施排列和对应物理坐标。fileciteturn713file0L2-L2

### 最需要修改的是 F2 的设施位置平衡

当前四族计划对 F2 主要采用：

> 主物体、盒子、秤、支架和目标一起平移。

这样会一直保留原来的相对设施排列。

但正式规范 D7.5 明确要求：

> 每种设施／关系在不同位置区域出现约 3～4 次，不能长期固定盒子在一边、秤在中间、支架在另一边。fileciteturn723file0L2-L2

**整体挪动几毫米，不能实现这个要求。**

这里不是要求 F2 再挑战某个很难够到的目标，而是需要 Astra：

1. 在已验证工作区内定义有限的设施排列模板；
2. 每个排列同时保证 inside/on/beside 的完整操作空间；
3. 将位置分配写入具体场景配置；
4. 在首批资格中验证，不把“计划了轮换”当成已经可行。

**不能用 `appearance_rotation` 这样实际不改变 F2 设施位置的字段，代替位置平衡。**

## 2. 难度目前还是“目标标签”，不是已经生成的几何事实

槽位写了：

```text
clear：2.2
medium：1.75
crowded：1.35
```

但还需要明确：**哪个对象对、哪个视角、按什么投影宽度计算，实际位置如何由这个目标生成。**

原规范还要求相应物体角色、可见性、独立抓取和不推动邻居；不能只给同一布局换一个 `difficulty` 字符串。fileciteturn719file0L2-L2

因此，下一版每个场景至少要生成：

```text
实际角色列表
资产绑定
各物体／设施位姿
目标区域
干扰物位置
预期难度及计算方法
必要净空与可见性条件
```

这些可以先是 **CPU 生成、物理待验证**，不需要在这一步就宣布全部可行。

## 3. 跨 split 的近重复，目前只有一句规则，没有实际检查

例如当前生成器中，F3 的一个 validation medium 槽位与一个 test medium 槽位，整体平移只差约 **4.47 mm**；两者的尺寸、资产和名义难度相同。对于 F2/F3，计划还明确不把无效 appearance 字段当成多样性。fileciteturn709file0L2-L2 fileciteturn713file0L2-L2

**这不代表“相差 4.47 mm 必定不允许”，而是不能只凭不同 ID、seed 和 hash 就宣布跨集合足够独立。**

建议在采集前冻结一个实用规则：

- 比较的是实际物体、设施和角色配置，不包括注释、ID、seed；
- 高度相近的派生布局放在同一 split，或重新安排有意义的布局差异；
- 不为了凑配额，采完后再修改相似性标准；
- 不需要训练模型来做这项检查。

# 三、第二项：计划校验器会放过一些明显无效的参数

我对原 `plan.validate()` 做了以下 CPU 反例：

| 修改 | 当前结果 |
|---|---|
| 将尺寸倍数改成 **−1** | 仍返回 `pass=true` |
| 将平移坐标改成 **NaN** | 仍返回 `pass=true` |
| 两个场景使用相同物理参数，只给其中一个加不同的无效备注字段 | 仍返回 `pass=true` |
| realization 声明中重复追加 `r_pc` | 仍可通过当前集合式检查 |

原因是当前校验主要检查数量、集合和整个参数字典的字符串是否不同，**没有严格检查参数类型、数值范围和真正的物理场景签名**。fileciteturn713file0L2-L2

另外，`generate()` 把同一份可变的 `REALIZATIONS` 列表交给多个槽位。修改一个槽位中的这份列表，会影响其他槽位甚至下一次生成结果。现在保存成 JSON 后彼此独立，但**未来在内存里做 reserve 激活或配置修订时，容易造成串改**。

### 必须补的内容

这部分不复杂，应该一次修掉：

```text
严格字段与类型
数值必须有限
尺寸与范围合法
意图／realization 无重复且恰好构成 3×3
每个槽位拥有独立配置对象
物理场景签名只由真正生效的参数生成
未知字段不能被当成“场景不同”的证据
```

**不要继续只增加一条“计划通过”测试；合法配置要通过，上述非法配置必须明确失败。**

# 四、第三项：reserve 规则在并行和难度继承时还没有闭合

原方案要求 reserve 激活后继承失败槽位的 split 和 difficulty，并留下追加式激活记录，不修改原 planned slot。这个方向正确。fileciteturn719file0L2-L2

但当前生成的 reserve：

```text
projected_spacing_width_ratio = null
```

还没有实现“继承后怎样确定性生成具体难度参数”的逻辑。fileciteturn713file0L2-L2

另外，同族允许并行两个或更多 root。若两个 root 先后失败，**不能因为哪个进程先结束，就随机决定 rank1 的 reserve 替代谁**。否则同一套计划在不同运行时序下会生成不同的数据集合。

建议预先定义：

```text
按冻结的失败槽位顺序分配 reserve
或者采用另一种明确、确定且可复核的分配策略
```

然后测试：

```text
两个 root 以不同顺序返回失败
→ reserve 不重复激活
→ 配额和继承结果符合冻结策略
→ 重启不再次消费 rank1
```

这是为了防止真正批量后出现重复场景和 split 混乱，**不是增加物理实验门槛**。

## 特别注意：严格前缀不能不加区分地扩大

正式规范规定，严格 P 属于三个 `r_pc` 的 `prefix_controlled` cohort；两个 `r_inv` 保留意图，但不应被强制纳入同一个严格 P 主分析。fileciteturn719file0L2-L2

需要完成的是**同一份正式 spec 从生成器贯穿到场景、目标、采集、变体、验收与副本**。下层不能重新根据 root 名称生成另一份默认配置。

# 六、第五项：副本小样证明“能独立读取”，但还不能防止错配和不完整包

**129 MB 小样成功的结论可以保留。**迁移测试确实安装了原路径访问拒绝规则，并从包内读取数据。fileciteturn716file0L2-L2 fileciteturn717file0L2-L2

不过，当前 `portable.py` 的验收能力仍较弱。我用文件哈希全部正确的小型合成包，复现了：

| 包内问题 | 当前 reader |
|---|---|
| `state` 的初始关节与 `trace.row0` 不一致 | 可以读入 |
| current state 含 NaN | 可以读入 |
| RGB 文件中没有任何相机图像 | 可以读入 |
| cell 是 beside，监督换成候选集内的 inside | 可以读入 |
| supervision 没列入校验清单，但另放一个同名文件 | 可以读入 |

**这些不是说现有小样已经坏了，而是说明新包一旦发生错配，当前 reader 检查不到。**源码主要检查文件自身 hash、state 长度、future 形状及“答案是否属于候选集”，尚未充分核对文件之间的关系。fileciteturn714file0L2-L2

## 复制时还需要一个关键绑定

当前复制程序会现场计算源文件 hash，再写入副本 manifest。

这能证明：

> 副本等于当时读到的源文件。

但还需要先证明：

> 当时读到的源文件，等于已验收来源索引所绑定的文件。

否则路径指错了、旧目录被替换了，也可能把错误内容连同新 hash 一起“正确复制”。

### 正式副本工具应满足

```text
封存来源索引中的预期身份
→ 实际源文件 hash
→ 副本 hash
→ 包内相对路径与角色
→ 原始数据之间的关联
```

尤其要检查：

- 必要相机集合、shape、dtype 和有限值；
- state 与 trace row0；
- action row0 的处理规则，避免对已经是 N 条的 action 再删一次；
- cell/program/realization 与监督一致；
- candidate、prefix、anchor 和验收来源；
- 必要文件均在 manifest 中，不能从未校验的固定路径偷偷读文件。

**不需要在每次普通读取时重跑整个物理 verifier。**物理验收结果以可信来源绑定；副本侧负责证明复制对象正确、内容完整、内部对应关系正确。

## 预算不必现在随意加大，但需要补三件事

**第一，接好真实入口后，生成每个阶段的调用表。**

首批再实测实际内存、写盘和复制吞吐。**不需要为了这件事做一个新的存储性能研究。**
