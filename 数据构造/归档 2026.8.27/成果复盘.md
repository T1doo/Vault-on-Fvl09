## 0. 一页结论

> [!success] 已完成的核心成果
> **4个accepted roots、24条formal raw trajectories、24份receipt、24份verifier、144个derived views、24条四视角MP4，以及一套完成最终seal的独立root小模型裁决链。**

这轮工作不是简单地“跑了几条RoboTwin轨迹”，而是从零搭建并实际跑通了一条**可审计的 controlled multi-future 数据与诊断实验链**：在同一个当前场景、同一个机器人状态下，分别生成“把同一只鼠标放到灰色垫子、电子秤、展示架”三个不同未来；每个目标又保留两条不同实现路径，用来区分“意图信息”和“某一条规划路径的指纹”。

截至2026-08-20，已经得到：

- 4个机器验收通过的独立root groups：`g_000007`、`g_000008`、`g_000011`、`g_000012`；
- 每组3个结构化目标，每个目标2条真实成功实现，即每组6条、合计24条formal raw trajectories；
- 24个HDF5、24份逐轨迹receipt、24份成功verifier、144个H/P、replacement和invariance派生view；
- 24条可直接观看的四视角MP4及逐视频验收记录；
- 一套共享候选打分小模型、动作suffix/delta表示、视觉proposal/embedding、独立root held-out裁决和最终结果封存链。

最终最准确的科研结论是：

> [!quote] 最准确的科研结论
> 使用在`g7+g8`上训练的“当前视觉embedding + future action step-delta + shared candidate scorer”，模型在没有参与训练、normalization或checkpoint选择的`g11/g12`上，通过了PC、同意图另一轨迹、future replacement、mask和候选排列等核心诊断。`L=2～256`的所有测试suffix长度均为core pass。但endpoint-only和temporal-shuffle在许多设置中也能取得同样高的结果，因此目前只能说future/Δaction内容具有跨独立root的诊断价值，尚不能说模型真正识别了动作时间顺序。

换成更通俗的话：

- 我们已经证明，数据里确实存在模型能跨新场景利用的“未来动作差异”；
- 我们还没有证明，模型必须按正确时间顺序理解这段动作；
- 因而不能把最早通过的`L=2`直接称作`H_reveal`；
- 当前不能进入动作压缩、π0.5或policy transfer结论。

> [!warning] 结论红线
> `first core L=2`不等于`H_reveal=2`；有效root数4不等于任务族正式泛化；derived view数144不等于144个独立统计样本。当前`h_reveal`必须保持为`null`。

本轮机器最终状态为：

```text
status = pass_independent_root_core_temporal_unresolved_v1
accepted roots = [g7, g8, g11, g12]
effective root N = 4
core passing L = [2, 4, 8, 16, 32, 64, 128, 256]
temporal contrast passing L = []
formal_generalization_claim = false
h_reveal = null
compression_or_policy_transfer_started = false
```

所以，这是一个很有价值的**数据构造与机制诊断阶段成果**，但还不是整个研究问题已经完成或论文主结论已经成立。

## 1. 这项工作研究什么

> [!question] 核心问题
> 在“现在”严格相同的条件下，只替换真实未来动作，模型的结构化目标预测会不会同步改变？

研究问题可以写成：在某个anchor时刻`t`，给模型同一个当前观察、当前机器人状态，再额外给一段从`t`开始的未来动作，它能否判断机器人接下来要完成哪个可验证的行为程序？

```text
current observation o_t
+ current robot state s_t
+ future action a[t:t+H]
                    ↓
structured intent / operation program
```

这里的“意图”不是心理动机，也不是一句自由文本解释，而是模拟器可以检查的结构化目标，例如：

```text
place(mouse, on_surface_of, gray_pad)
place(mouse, on_surface_of, electronic_scale)
place(mouse, on_surface_of, display_stand)
```

未来动作只在训练或机制诊断时作为privileged evidence。正常机器人策略部署仍然是：

```text
current observation + current robot state + normal instruction -> action chunk
```

部署时不会获得专家未来动作、未来RGB、未来物体位姿、成功谓词或planner目标。

本研究也不声称“未来动作在物理上造成了意图”。真实生成方向始终是：

```text
intent / program -> planner与controller产生trajectory
```

模型实验只是在反方向检查：给定不同的真实future，预测是否跟随future切换到相应的结构化程序。

## 2. 为什么不能直接使用RoboTwin官方数据

> [!warning] 官方episode只能证明pipeline能跑
> 三个官方任务分别重建场景，mouse、机器人状态、布局和图像都不同。直接拼起来训练，模型可能通过场景差异猜答案，不能证明future action本身有价值。

最开始分别跑通了三个官方任务：

- `place_mouse_pad`；
- `place_object_scale`；
- `place_object_stand`。

这些普通episode证明了RoboTwin的planner、controller、相机、HDF5和视频流程能运行，但它们不能组成受控多未来数据：三个任务各自重新建场景，mouse实例、机器人当前姿态、物体布局、相机图像和随机条件都不相同。

如果直接拿它们训练，模型很可能通过场景差异猜目标，而不是根据未来动作判断目标。因此需要新建一种数据单位：**controlled multi-future root group**。

一个root group要求：

```text
同一个联合场景：mouse + pad + scale + stand
                         ↓
同一份current context与物理等价anchor
                         ↓
先冻结三个可行candidate programs
              ┌──────────┼──────────┐
              ↓          ↓          ↓
          mouse→pad  mouse→scale  mouse→stand
              ↓          ↓          ↓
         r_pc + r_inv r_pc + r_inv r_pc + r_inv
```

这样，组内六条轨迹共享的是“现在”，变化的是“未来要完成什么”和“用哪条路径完成”。

> [!info] Root group是统计基本单位
> 一条trajectory不是一个独立实验样本。同一个root派生出的所有branch、H/L切片、replacement、mask和视频都必须留在同一split中。

## 3. 整个工作是怎样一步步完成的

### 3.1 先确认官方环境和动作语义

第一阶段不是立刻采数据，而是审计RoboTwin到底记录了什么：

- 验证fvl05上的SAPIEN、CuRobo、相机渲染和GPU环境；
- 确认官方`joint_action`实际主要是drive target与夹爪命令，并不是完整的realized qpos或速度；
- 确认控制频率为250 Hz，即每步0.004秒；
- 明确动作和状态必须满足`N actions / N+1 states`的时间关系；
- 明确planner target、controller request、effective setpoint、drive readback和realized state必须分开保存。

这一阶段形成了snapshot、动作、时间对齐、模型可见性和运行时验证的基础合同。

### 3.2 冻结数据规范，再写隔离实现

随后冻结了scene spec、对象引用、候选程序、task tree、attempt预算、verifier、failure记录和Gate。新实现以additive方式放在独立package、script和tests下，没有修改三个官方任务的tracked基线。

最关键的设计包括：

- 场景先于意图选择，三个candidate必须在主planner rollout前冻结；
- 每个失败attempt也保留，不能只保存成功轨迹；
- raw-first：采集时保存完整原始动作、状态、时间、验证与provenance，不在采集阶段压缩；
- 模型只读白名单字段，禁止读取intent ID、branch ID、planner path、future object state、verifier truth等答案泄漏字段；
- 所有恢复采用新版本和新namespace，不覆盖旧失败文件。

### 3.3 运行时认证暴露了真正困难的物理问题

> [!failure] 最难的问题来自物理状态，而不只是planner
> snapshot恢复、contact cache、sleep状态、支撑物body type、相机可见性和scene生命周期都会造成“画面看起来一样、物理上却不等价”。最终采用fresh-scene reconstruction作为严格分支边界。

联合Mouse场景的难点不只是“planner能不能走到”，还包括：

- pad在画面里最初只有约4个像素，机器可见但人和模型难以识别；
- 物体贴近画面边缘，必须增加完整入镜和边距Gate；
- SAPIEN scene snapshot不能稳定清除所有历史contact cache；
- dynamic scale/stand会让支撑物自身运动，破坏稳定性验证；
- 相同场景里反复恢复后，dynamic-support接触历史可能污染后续branch。

经过多轮不降低Gate的probe，最终确认：**fresh local scene reconstruction**才是严格可重复的branch边界。每条关键运行都重新创建scene、恢复相同anchor、验证拓扑和状态，结束时关闭scene lease。

scale和stand也被明确绑定为static support，避免把支撑物本身的运动误当成鼠标放置失败。

### 3.4 从失败root恢复出g7和g8

早期g3、g4、g5、g6都有不同失败，全部保留：

- g3/g5暴露视觉与稳定性Gate问题；
- g4在独立stand RT-08上失败；
- g6已经通过scene认证，但collector漏做scene revision runtime binding，五次prefix attempt都在规划前因scale body type不一致失败，最终保持0条raw；
- g6没有被原地修补，新增g7 recovery lineage；g6和g7属于同一个root-equivalence class，统计时最多算一次。

g7最终完成6/6正式轨迹、raw finalize、WP-E派生和G6。随后新建独立g8，经过新的布局恢复、认证和版本化finalizer后也完成6/6。至此先获得两个development roots，共12条raw。

### 3.5 先在g7/g8上训练小模型，而不是盲目扩数

两个root完成后，先训练最小shared scorer，问题暴露得很清楚：完整future比current-only好，但只看endpoint同样好，replacement后预测完全不切换。

因此没有把53.3%包装成成功，而是冻结失败run，继续做suffix/delta诊断。

### 3.6 suffix/delta显示方向正确，但两root泛化仍不稳定

把公共前缀后的suffix切成：

```text
L = {1, 2, 4, 8, 16, 32, 64, 128, 256} steps
```

并比较：

- absolute suffix；
- branchpoint residual；
- step delta；
- residual + step delta。

新future encoder显式保留first、mean、max-abs、last特征，避免长公共前缀把最早分叉信号淹没。

结果表明step-delta明显减小了不同root之间的绝对动作offset，短suffix在训练root上也有学习能力；但是g7↔g8的正式双向评测仍受seed、root和路径影响，没有任何L通过全部预注册Gate。因此这一步仍判hard fail，而不是挑一个好seed宣布成功。

### 3.7 补视觉grounding，并定位root-specific shift

进一步审计发现，仅有动作delta仍可能无法理解“这个方向在当前场景中对应哪个目标”，所以加入当前视觉信息。

这条线经历了三层迭代：

1. 第一版visual foundation因feature cache的真值来源不符合输入合同而失败，未用于正式意图训练；
2. RGB/text-only visual proposal recovery通过开发集可识别性，但正式跨root实验暴露proposal分布随root变化；
3. 改用更稳定的patch/visual embedding后，CPU capacity能学会开发root，但正式独立seed仍出现root-specific future mapping与seed instability。

这些失败说明，问题不是简单地“模型再大一点”或“多跑几个epoch”就能解决。已有两个root已经被反复用于设计与诊断，不能再把它们当作从未见过的泛化证据。

### 3.8 为什么后来又采了g11/g12

> [!question] 不是说先不采新数据吗？
> 是的。先不扩数是为了用g7/g8判断模型与表示是否有基本能力；这个诊断完成后，g7/g8已经变成development data。要做未见场景裁决，就必须冻结方案后再构造新的独立root，因此才新增g11/g12。

最初“不采新数据”的建议是合理的：先用g7/g8确认旧模型是否有基本表示能力。这个任务完成后，g7/g8已经成为development data。

要回答“修好的表示能否迁移到新的独立场景”，必须再准备从未用于模型选择的新root。因此预注册了independent-root adjudication，并尝试新布局：

- g9/g10的全局平移布局18个候选全部失败，主要是front-camera可见性与双接触可达性问题；没有创建formal raw；
- 改为role-conditioned、约4 cm的布局修复，新建真正独立的g11/g12；
- 两组均重新通过scene、视觉、接触、IK、orientation、fresh-scene和exact-entry认证，再各采6条正式轨迹。

g11/g12不是g7/g8的改名或复制，也不是失败组的relabel。它们具有新的scene/root/anchor和布局，被严格保留为一次性held-out adjudication roots。

### 3.9 最终独立root裁决与结果封存

最终模型只使用g7+g8训练及拟合normalization。所有表示、L网格、模型结构和checkpoint规则在查看g11/g12结果前冻结；g11/g12不参与训练、normalization、early stopping、checkpoint选择或阈值选择。

最终正式run保存：

```text
9个L × 3个model seed = 27个fixed-last checkpoints
```

运行后又逐个hash并以`weights_only=True`重新加载27个checkpoint，重新做四root full closure，最后生成write-once final seal。机器结论保持为`core pass / temporal unresolved`。

### 4.4 一条HDF5里保存什么

> [!tip] 最简单的理解
> HDF5同时保存“机器人被要求怎么动”“模拟器实际处于什么状态”“这一步发生在什么时候”和“成功判定依据是什么”。模型只读取其中经过白名单筛选的一小部分，其他字段只用于审计。

一条raw trajectory不是只有关节角，而是同时保留了：

```text
time/
  action start/end time与step
  state time与anchor-relative step

action/planner/
  planner位置、速度、segment、path index与valid mask

action/command/
  requested arm position/velocity/gripper
  effective arm position/velocity/gripper
  component update mask

action/drive_readback/
  simulator drive target与gripper readback

state/robot/
  full qpos/qvel
  双臂qpos/qvel、夹爪实现状态、EEF pose

state/object/
  mouse、pad、scale、stand的pose、速度、dynamic/sleeping状态

state/contact与state/predicate/
  接触关系、目标关系、稳定性和verifier状态

events/
  approach、grasp、lift、transport、release等事件边界
```

审计信息很丰富，但模型不能全部读取。当前primary future stream只有：

```text
12维双臂effective position target
+ 12维双臂effective velocity target
+ 2维normalized gripper command
= 26维/step
```

模型还可读取时间和component update mask。planner/path、future object state、contact、verifier、group/branch/intent ID和hash都留在模型外。

### 4.5 current observation怎样处理

每个root有一份经过hash绑定的current context，六条branch共同引用它。它包括：

- `head/front/left/right`四个相机的current RGB和calibration；
- anchor时刻的双臂qpos、qvel和夹爪状态；
- scene topology、物理状态hash与source lock。

组内六条branch的current必须相同；不同root之间的current和物体布局允许不同，这正是跨root评测要面对的变化。

formal raw没有采集一整段future RGB。模型使用的是current视觉加future action；后来的MP4是根据已记录状态重新渲染的人工检查视频，不是collection-time future RGB，也没有进入训练。

### 4.6 派生view是什么

每个root有36个只读derived views：

- 30个natural-H views；
- 6个三个`r_pc`目标之间的有向future replacement views。

派生层不复制raw action数组，只保存raw引用、切片边界、slice hash、target和可见性合同。四个root合计144个views，但统计上仍只有4个root，不能把144当作144个独立样本。

replacement的含义是：current保持不变，把future A换成同组真实future B，同时把监督目标切换为intent B，检查模型预测是否严格跟着切换。

## 6. 小模型怎么训练、为什么要经历多版

### 6.1 任务不是固定三分类，而是候选排序

模型同时看到三个结构化candidate programs，用同一个shared scorer分别打分：

```text
score(current, future, candidate_program_1)
score(current, future, candidate_program_2)
score(current, future, candidate_program_3)
```

三个候选的展示顺序随机化并做permutation test，模型不能使用固定class ID或候选位置猜答案。这种设计将来可以扩展到新的结构化程序，而不是永远绑定本地的“类别0/1/2”。

### 6.2 第一版tiny model：证明了endpoint陷阱

> [!failure] 53.3%不是成功
> raw future虽然比chance高20个百分点，但endpoint-only也是53.3%，replacement strict switch为0%。模型学到的是“最后到了哪里”，没有学会future被替换后应同步切换目标。

路径：

```text
/nfs_share/lijunhui/Robotwin2/models/future_action_intent_mvp/
  wp_g0_tiny_diagnostic_v1/run_000001
```

模型约45,025个参数，使用两层temporal Conv和mean/max/last pooling；视觉接口当时为零权重，只做动作与状态诊断。训练采用两个leave-one-root-out方向、3个seed、5种输入变体，共30个fixed-last checkpoints，无validation或test选模。

| 指标 | 结果 |
| --- | ---: |
| current-only Top-1 | 33.3% |
| correct full raw future Top-1 | 53.3% |
| endpoint-only Top-1 | 53.3% |
| replacement target accuracy | 33.3% |
| strict replacement switch | 0% |
| same-intent consistency | 100% |
| candidate permutation score delta | 0 |

结论：future中有信号，但模型主要看终点；当future被替换时预测不切换，核心Gate失败。

### 6.3 suffix/delta model：找到更合理的动作表示

> [!success] 重要方向性发现
> raw absolute action存在明显root offset；转成step-delta后，同意图跨root的距离明显缩小，短分叉信号更容易被模型看到。

路径：

```text
/nfs_share/lijunhui/Robotwin2/models/future_action_intent_mvp/
  wp_g0_suffix_delta_v1/run_000001
```

该实验比较4种表示、9个L、2个fold、3个seed，共216个checkpoint。future encoder显式使用first、mean、max-abs、last，保护刚分叉的早期信号。

主要发现：

- step-delta比absolute suffix更能消除不同root的绝对姿态offset；
- 在开发root上短suffix可以被模型学到；
- 正式g7↔g8结果仍有seed/fold/path不稳定；
- endpoint与temporal shuffle经常追平自然future；
- 没有L通过全部预注册Gate。

机器状态因此是：

```text
hard_fail_suffix_delta_diagnostic_no_expansion_no_compression_no_policy_transfer
```

这不是“delta没用”，而是“delta方向有明显改善，但只靠两个反复使用的root还不足以给出稳健结论”。

### 6.4 视觉proposal与embedding：解决动作方向的场景含义

后续版本加入当前视觉。视觉backbone资产保存在：

```text
/nfs_share/lijunhui/Robotwin2/models/future_action_intent_mvp/
  vision_backbones/owlvit-base-patch32-cbc355fb3645
```

实验先后经历visual foundation、RGB/text-only proposals、proposal+delta、patch embedding+delta。每次失败都保留并由新版本恢复，没有覆盖旧run。

阶段性结论是：

- 当前视觉是必要的，因为同一动作方向在不同root布局中可能指向不同目标；
- proposal级特征有较强root-specific shift；
- patch embedding更稳定，能通过开发集capacity；
- 但只在g7/g8做双向formal时，独立seed仍不能稳定复现core，说明未来动作到目标的映射仍受root覆盖度影响。

## 7. 最终模型结果与应当怎样解释

### 7.1 核心正结果

> [!success] Final core diagnostic pass
> 从`L=2`到`L=256`，三个seed都在四个root上同时通过PC、r_inv、directed replacement、mask、candidate cycle和candidate permutation核心Gate。

在`L=2、4、8、16、32、64、128、256`上，三个seed都同时满足：

- g7/g8/g11/g12的三条`r_pc`均3/3正确；
- 同意图`r_inv`均3/3正确；
- 三意图之间六个有向future replacement均6/6严格跟随future切换；
- future mask、vision mask、semantic mask符合预期；
- candidate cycle与candidate permutation Gate通过；
- g11/g12从未用于训练、normalization或checkpoint选择。

`L=1`时，四root的PC和replacement仍通过，但g11的`r_inv`只在一个seed达到满分，因此L=1不算完整core pass。

这说明新模型不是只记住g7/g8某一条路径：同目标换一条实现仍能判断；换成另一目标的真实future时，预测也会切换；而且这一现象迁移到了两个独立新root。

### 7.2 仍未解决的关键问题

> [!warning] Temporal unresolved
> 自然顺序future没有稳定优于temporal shuffle或endpoint-only。模型可能利用Δaction的方向、幅度、集合或终点，而不一定理解动作先后顺序。

没有任何L通过temporal contrast Gate。原因是：

- temporal-shuffle在许多L、seed和root上仍然满分；
- endpoint-only也经常达到满分；
- 因而自然顺序future没有稳定、系统性地优于“打乱顺序”或“只看终点”。

这意味着模型可能主要使用了step-delta的集合、方向、幅度或终点线索，而不是理解完整动作顺序。

### 7.3 为什么`L=2`不能叫H-reveal

> [!danger] 禁止把8 ms写成正式H-reveal
> `L=2`是从已知branchpoint后截取的两步suffix，不是从anchor开始的输入可观察H；且时间控制项没有通过。当前只允许写`first_core_passing_horizon_steps=2`和`h_reveal=null`。

250 Hz下，2步约为8 ms。看到模型从branchpoint后2步就能完成core诊断是很有趣的，但不能直接写成“8 ms就是意图显现时刻”，原因有三点：

1. L是对齐到已知branchpoint后的suffix长度，不是从anchor开始的完整H；
2. branchpoint对齐本身来自审计信息，不能混成部署输入；
3. temporal shuffle和endpoint对照没有被稳定击败。

所以当前字段必须保持：

```text
first_core_passing_horizon_steps = 2
h_reveal = null
```

### 7.4 当前能说和不能说什么

可以说：

1. controlled multi-future raw-first数据构造、验证、派生、视频和跨版本读取管线已跑通；
2. 24条formal raw全部有机器闭包和可追溯失败/恢复历史；
3. step-delta比绝对动作更适合跨root表示早期分叉；
4. 当前视觉embedding + step-delta模型在两个group-disjoint新root上通过了core diagnostic transfer；
5. replacement和same-intent alternative path结果说明模型不是只用固定candidate位置或单一路径ID。

不能说：

1. 不能说已经证明动作时间顺序理解；
2. 不能把`L=2`称为正式`H_reveal`；
3. 不能把有效root N=4写成任务族或scene-family的正式泛化；
4. 不能把144个derived views当作144个独立样本；
5. 不能开始宣称compression/K结论；
6. 不能宣称π0.5训练、policy transfer或rollout提升；
7. 不能继续把已经查看过结果的g11/g12当作“从未触碰的holdout”。

## 8. 遇到的主要问题以及学到什么

> [!abstract] 这一轮最重要的方法论经验
> 每次失败都应回答“数据、物理、表示还是验证合同哪里不成立”，而不是通过删证据、改seed、放松阈值或重复训练把结果做绿。

### 8.1 “看起来相同”不等于物理状态相同

仅恢复pose不够，contact cache、sleep状态、支撑物body type和controller内部状态都可能造成差异。最终采用fresh-scene lifecycle和完整anchor bundle，而不是依赖同一个scene反复倒带。

### 8.2 可见性Gate需要人工与机器共同校准

早期pad虽然通过“非零像素”检查，但只有4 px，科研上不可接受。后来增加面积、完整入镜、边距和多相机检查。这个过程避免了“机器Gate绿色，但数据实际看不清”的假成功。

### 8.3 支撑物必须符合任务物理设计

dynamic scale/stand会导致鼠标与支撑面一起运动，污染稳定性和接触判断。static-support revision解决了物理定义问题，但也引出了g6 collector漏绑定scene revision的集成失败。教训是：scene certification与正式collector必须走同一exact entry和同一调用顺序。

### 8.4 失败不能靠重命名或删文件消失

g6没有被修成“成功g6”，而是冻结失败、创建g7 recovery并建立hash bridge；g4、g9、g10也保留为真实失败证据。这样统计时不会把一个root的多次恢复重复计数。

### 8.5 finalizer不能只数HDF5

六个HDF5并不等于数据完整。finalize还必须核对reservation、attempt terminal、receipt、verifier、collection result、fresh-scene lifecycle、GPU pre/post和无orphan关系。这一严格Gate多次暴露了promotion/finalizer阶段合同问题，也防止了“文件写了一半就宣布完成”。

### 8.6 CUDA环境污染确实发生过

> [!danger] 必须长期保留的防复发规则
> RoboTwin GPU child不能直接继承外层shell的CUDA/Python环境。必须清除外部CUDA路径，固定项目CUDA 12.1、项目Python和workspace cache/tmp，并在每次GPU执行前后检查physical GPU0。

g12第一次formal run在0 attempt、建scene之前失败。根因是child继承了外部`/share/apps/cuda/12.2/lib64`路径，Torch加载`libnvJitLink.so.12`时出现I/O错误。

后续新增了统一的sanitized child environment：清除外部CUDA/Python变量，固定项目CUDA 12.1、项目Python和workspace cache/tmp。新版本通过poisoned-environment regression、最小CUDA certification和正式6/6采集。这个错误没有消耗正式attempt budget，也没有被隐藏。

### 8.7 NFS全量验证成为明显瓶颈

> [!note] Fast不会替代Full
> phase-aware fast Gate只绑定已经通过full的closure receipt。首次验收、finalize、dataset acceptance、final promotion和final seal仍必须重新做full hash。

最后一次四root full closure重新hash 24个HDF5并materialize arrays，耗时14,241.22秒，约3小时57分钟。结果通过，但说明普通后续Gate不能反复全扫NFS。

因此实现了phase-aware fast/full validation：

- 首次receipt、finalize、dataset acceptance、final experiment promotion和final seal仍执行full；
- immutable raw通过full后生成版本化closure receipt；
- 普通检查只绑定receipt、source lock、Merkle/小闭包，不重复读取全部HDF5；
- fast validation约数秒，并明确写`current_hdf5_bytes_rehashed=false`，不冒充full。

当前没有已验证的workspace-local NVMe mirror，因此没有虚构“本地盘加速已经完成”。

### 8.8 模型失败比一个漂亮数字更有价值

第一版53.3%看似比chance好，但endpoint相同、replacement为0，说明它没有学到我们真正关心的机制。后续每次都保留hard fail，而不是换seed、加epoch或挑最好结果。正是这些失败一步步定位出：

- 绝对动作有root offset；
- step-delta更稳定；
- 需要当前视觉解释动作方向；
- visual proposal有root shift；
- 两个development root不足以作独立裁决；
- 最终core可迁移，但时间顺序仍未识别。

### 8.9 视频链也遵守版本化恢复

g11/g12视频v2 smoke因错误调用pre-promotion validator而在建scene前安全失败。没有修改已执行v2，而是新增v3，hash绑定失败证据并切换到正确post-promotion validator。v3 smoke和正式12/12通过，GPU0完整释放。
