## 0. 一分钟看懂这 24 条视频

四组数据都在做同一件事：

```text
同一只鼠标 + 同一台机器人 + 同一个当前场景
                         ↓
       分别走向三个不同、可验证的未来目标
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       灰色垫子        电子秤          展示架
          ↓              ↓              ↓
      两种成功路径    两种成功路径    两种成功路径
```

因此每个 group 有：

- 3 个 structured intents：鼠标放到垫子、电子秤、展示架；
- 每个 intent 有 2 条真实成功 realization；
- 每组 `3 × 2 = 6` 条轨迹；
- 四组一共 `4 × 6 = 24` 条轨迹。

> [!abstract] 最重要的区别
> **同一个 group 内**，六条轨迹从同一份 current context 和物理等价 anchor 出发，主要比较不同 future。
> **不同 group 之间**，鼠标、垫子、电子秤和展示架的初始摆放位置不同，用于检查模型能否跨场景 root 使用 future action，而不是记住某一张固定画面。

这 24 条视频均为：

- 四相机 `head / front / left / right` 的 2×2 拼图；
- H.264 MP4，`640×520`，`25 FPS`；
- 每 10 个 250 Hz recorded state 取一帧，并保留 terminal state；
- 单条约 `8.64～10.00` 秒；
- 总大小 `14,909,200 bytes`，约 `14.22 MiB`。

> [!warning] 视频的用途边界
> 这些 MP4 是对已验收 HDF5 中 recorded states 的**人工审阅播放**。渲染视频时没有重新运行 planner、controller 或物理 rollout；视频不是模型输入，也不是新采的 formal trajectory。

## 1. 什么叫 controlled multi-future root group

普通 RoboTwin episode 往往每次都重建场景。如果分别运行“放到垫子”“放到电子秤”“放到展示架”，三条 episode 的物体布局、机器人状态和当前图像都会不同，模型可能只看场景差异就猜出答案。

本项目改用受控 root：

1. 先创建一个同时包含 mouse、pad、scale、stand 的联合场景；
2. 在选择具体 intent 之前，冻结三个可行候选目标；
3. 保存一次共同的 current context 和物理等价 anchor；
4. 从这个共同“现在”分别产生三个不同的未来；
5. 每个未来再保留两种成功路径；
6. 保存原始 action/state/time、失败记录、receipt、verifier 和 provenance；
7. 只有六槽、生命周期、哈希与成功 Gate 一一对应时，group 才能被接受。

因此真正的统计基本单位是一个完整 root group，而不是把 24 条轨迹当成 24 个互相独立的实验样本。

```text

奇数 → r_pc
偶数 → r_inv
```

## 3. 一组数据是怎样构造出来的

### 3.1 先定场景，再定目标

每个 group 先确定 mouse、pad、scale、stand 的布局，验证：

- mouse 是唯一被操作的动态物体；
- pad、scale、stand 都是静态支撑物；
- 三个目标区域互不重叠；
- 根状态稳定，且三个目标在同一机械臂可达范围内；
- 根状态下尚未提前满足任何目标。

三个候选 program 随后被冻结：

```text
place(mouse, on_surface_of, gray_pad)
place(mouse, on_surface_of, electronic_scale)
place(mouse, on_surface_of, display_stand)
```

### 3.2 `r_pc`：三个目标共享严格公共前缀

`br_000001 / 000003 / 000005` 属于 `prefix_controlled` cohort。三条轨迹先共享同一段 canonical approach、grasp 和 intent-neutral lift，只有走到 branchpoint 后才朝三个目的地分叉。

四组实际公共前缀长度为：

| group | `P_steps` | 250 Hz 下对应时间 | 主要用途 |
| --- | ---: | ---: | --- |
| `g_000007` | 1154 | 4.616 s | development |
| `g_000008` | 1154 | 4.616 s | development |
| `g_000011` | 1151 | 4.604 s | held-out adjudication |
| `g_000012` | 1157 | 4.628 s | held-out adjudication |

> [!note] 为什么不同 root 的 P 不完全相同
> `P` 是某个具体 `prefix_controlled` cohort 的真实公共 action 前缀长度，不是写死的全局常数。g11 和 g12 的场景布局不同，规划和控制轨迹长度也会略有变化，所以不能把 g7/g8 的 `1154` 强行套到新 root。

### 3.3 `r_inv`：同一目标的另一条成功实现

`br_000002 / 000004 / 000006` 是相应 intent 的另一条成功 realization，用来检查模型是否只记住一条 planner/path 指纹。

它们与对应的 `r_pc`：

- current context 和最终目标相同；
- 都通过相同的 simulator verifier；
- 但采用不同的接触/姿态 witness 和独立路径；
- 不要求套用 `r_pc` 的严格公共前缀 `P`。

在冻结六槽中，`r_pc` 使用 contact witness 0，`r_inv` 使用 contact witness 1；pad/stand 使用 orientation witness 10，scale 使用 orientation witness 0。这里的编号只是版本化构造合同，不是模型可见标签。

### 3.4 Raw 数据记录什么

正式模型使用的是 HDF5 中的 raw-first 数据，而不是 MP4：

- 250 Hz、26 维 `controller_effective_setpoint_v1`；
- 12 维 arm position target；
- 12 维 arm velocity target；
- 2 维 normalized gripper command；
- action/state 时间戳与 component update mask；
- 严格满足 `N actions / N+1 states`；
- 当前四相机 RGB、机器人与场景状态；
- 逐轨迹 receipt、verifier 和 fresh-scene lifecycle provenance。

目标 ID、branch ID、planner path、future object pose 和 verifier truth 不会作为正常模型输入。

## 4. 为什么 1/2、3/4、5/6 看起来差别不大

这是正常现象，不是视频重复或构造失败。

比如 `br_000001` 和 `br_000002`：

- 起点相同；
- 都要抓同一只 mouse；
- 终点都在同一块 pad；
- 成功后的静止画面几乎一致；
- 差别主要存在于中间的 approach、接触姿态、关节路径和速度变化。

此外，原始控制流是 250 Hz，而视频是 25 FPS，相当于每 10 个 recorded state 展示一帧；一些持续时间很短的 Δaction 差异在普通速度下不显眼。

> [!tip] 怎样更容易看出两条 realization 的区别
> 同时打开同一目标的一奇一偶两条视频，把进度条拖到“手开始靠近 mouse”“夹住后抬起”“转向目标”的中间阶段，使用 0.25× 或逐帧播放。重点看机械臂接近角度、手腕姿态、抬起后的弧线和到达目标前的修正，不要只比较首帧和末帧。

这两条轨迹的研究作用也不是要求肉眼一眼就能分开，而是验证：模型在路径有所变化时，是否仍能认出它们属于同一个结构化 intent。

> `g_000006` 是不可变失败证据，raw 为空；`g_000007` 是其版本化 recovery。两者属于同一个 root-equivalence class，最多只能统计一次。最终 accepted roots 是 g7、g8、g11、g12，有效 root 数为 4，不是 5。

### 5.3 g7 为什么叫 recovery，g11/g12 为什么后来才采

`g_000007` 不是“把旧 g6 文件改名”。g6 collector 曾漏掉在 scene construction 前把环境 design 从 base r1 绑定到经认证的 r3，六次采集因此在规划前安全失败。g6 被永久保留，g7 使用新版本 config、collector、CLI、wrapper 和 recovery-certification bridge，逐 hash 绑定 g6 的认证证据，再重新采集。

g7/g8 最初足够用于开发模型，但它们同时参与 representation、normalization 和模型选择，不能再作为外部泛化证据。为做一次 group-disjoint 裁决，先冻结方案，随后才采 g11/g12；训练和 normalization 仍只用 g7/g8，g11/g12 只用于最终 adjudication。

> [!important] held-out 已经被使用
> g11/g12 在最终裁决中已经被查看和使用，因此从现在起不能再称为“从未触碰的 holdout”。如果后续还需要新的外部裁决，必须在新方案冻结后再构造新的独立 root。

## 6. 推荐观看顺序

### 第一轮：先理解三个目标

先看同一 group 的三条 `r_pc`：

1. `br_000001`：pad；
2. `br_000003`：scale；
3. `br_000005`：stand。

建议从 g7 开始。你会看到前半段抓取和抬起很接近，后半段才分别转向三个目标。

### 第二轮：看同目标的不同路径

依次比较：

- `br_000001 ↔ br_000002`；
- `br_000003 ↔ br_000004`；
- `br_000005 ↔ br_000006`。

重点看中间运动，不要只看最终放置位置。

### 第三轮：跨 group 看场景变化

固定同一 branch，例如连续查看四组的 `br_000001`。目标始终是 pad，但场景布局和动作路径会随 root 改变。这最直观地展示了“语义不变、root 改变”的测试条件。

### 第四轮：理解模型裁决

最后比较 g7/g8 与 g11/g12：前两组用于开发和训练，后两组用于一次冻结后的独立 root 裁决。模型的正结果不是来自“看过 g11/g12 再拟合”，而是检查 g7/g8 学到的 future/Δaction 表示能否迁移过去。

## 10. 这四组数据支持了什么结论

g7/g8 用于 development；最终模型只在这两组上训练、拟合 normalization 和选择 checkpoint。冻结后，模型在 g11/g12 上做一次独立 root adjudication。

最终机器状态是：

```text
pass_independent_root_core_temporal_unresolved_v1
```

通俗解释：

- 模型学到的 future/Δaction 内容可以迁移到两个新场景 root；
- PC、同意图另一轨迹、replacement、mask 和候选排列等 core tests 通过；
- 但 temporal shuffle 与 endpoint-only 对照没有稳定变差；
- 因此尚不能说模型真正理解了动作时间顺序；
- `L=2` 不能写成正式 `H_reveal=2`；
- compression 和 policy transfer 仍未启动。

> [!success] 已经成立的阶段性成果
> 受控多未来数据构造、四 root raw/derived closure、跨独立 root 的 core diagnostic transfer 和完整可审计视频链已经成立。

> [!caution] 尚未成立的科研结论
> 正式时间顺序识别、H-reveal、压缩优势、任务族泛化和策略迁移尚未成立。24 条 trajectory 也不能替代更多独立 root 的统计证据。
