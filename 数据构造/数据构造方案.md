# Controlled Multi-Future 数据构造与实验总方案

> [!abstract] 唯一 canonical 执行入口
> 本文合并 F1–F4 数据构造、phase-1 机制模型训练评测和未来 π0.5 接入三类职责。科学设计版本仍为 `controlled_multi_future_f1_f4_v1_2`；`merged_master_v1` 只表示文档结构合并，不改变 candidate programs、40/360 分母、5/2/3 split、action stream、verifier semantics 或 Temporal Gate。

> [!danger] 仅授权有限非正式验证
> 用户只授权 `controlled_multi_future_runtime_v3_3` 冻结预算内、one-shot guard 保护的 pre-Stage-0 nonformal probes。Stage 0/1/3、正式轨迹采集、机制模型训练、H-reveal、compression 和 π0.5 继续禁止。非正式 root 成功不等于 Stage 0 授权。

## 总览：职责、状态与阶段依赖

| 组件 | 规范状态 | 实现状态 | 授权状态 | 当前职责 |
|---|---|---|---|---|
| 数据构造与验收 | **Frozen** | runtime implementation partial / blocked | 未授权采集 | F1–F4 scene、slot/candidate、raw、verifier、split、Gate、seal |
| 机制模型训练与评测 | **Deferred / not started** | not started | not authorized | model family、representation、H sampling、normalization、checkpoint、root-level statistics、test seal |
| 多任务训练混合与 π0.5 | **Deferred / not started** | not started | not authorized | 未来 mixing、loss、loader、shared parameters、rollout；主路线需先通过 K Gate |

固定阶段依赖：


### D1. 这一批数据只回答四个问题

现有 Mouse 数据是 S2 目的地选择：同一只 mouse 去 pad／scale／stand。它已经支持 future-content、replacement prediction-switch 与 cross-realization diagnosis，但 endpoint／净位移／动作统计可能已经足够，时间顺序仍未证明。

下一批数据固定回答：

| 问题 | Family | 主要排除的捷径 |
|---|---|---|
| 操作当前图像中的哪个具体对象？ | F1 | 固定左／中／右方向标签、object position shortcut |
| 同一对象要执行哪个目标—关系组合？ | F2 | 只识别方向、不绑定 object–target–relation bundle |
| 相同起终态与相同动作原语集合中，过程顺序是什么？ | F3 | endpoint、均值／方差、无序 action multiset |
| 相同对象、子任务集合和最终世界状态中，高层执行顺序是什么？ | F4 | final-state recognition、subtask bag-of-events |

F1/F2 负责 **future content + visual grounding**；F3/F4 负责 **Temporal Identifiability**。F2 第一版只证明 object–target–relation program bundle grounding，不证明 relation 与 facility 已解耦或具有组合泛化；F2 允许 endpoint-only 有一定效果，也不能单独承担动作顺序结论。

> [!danger] 不允许的退化方案
> 不能只把 mouse 换成 bottle、把 pad 换成 box、把三个目的地扩成更多目的地；也不能用“竖直摇／水平摇／旋转”三个动作集合不同的标签冒充顺序任务。F3/F4 必须让 endpoint、事件 multiset 与静态终态尽量一致，真正变化的只有过程顺序。

### D2. 冻结规模与数据分母

#### D2.1 正式规模

| 数量项 | 冻结值 |
|---|---:|
| 核心场景族 | 4 |
| 独立 roots / family | 10 |
| intents / root | 3 |
| successful realizations / intent | 3 |
| formal raw trajectories / root | $3\times3=9$ |
| **formal accepted independent roots** | **40** |
| **formal raw trajectories** | **$4\times10\times3\times3=360$** |
| planned ordered reserve slots | 4 / family = 16；不进入 formal denominator |

```text
40 个真正独立的 current
× 每个 current 下 3 个 structured programs
× 每个 program 3 条不同真实成功 rollout
= 360 条 formal raw trajectories
```

#### D2.2 Family 分配

| Family | roots | raw trajectories | 任务角色 |
|---|---:|---:|---|
| F1 | 10 | 90 | 对象 grounding |
| F2 | 10 | 90 | 目标—关系组合 grounding |
| F3 | 10 | 90 | 低层动作事件顺序 |
| F4 | 10 | 90 | 高层多物体子任务顺序 |
| **总计** | **40** | **360** | F3/F4 恰占正式数据一半 |

#### D2.3 默认不计入正式 360 的数据

- Stage 1 累积得到的 48 条 mechanism pilot trajectories；其中已包含 Stage 0 最早采出的 12 条 `r_pc` smoke，并非 `12+48=60`；除非按下述 promotion 条件进入 formal train；
- 现有 Mouse g7/g8/g11/g12 的 24 条 raw trajectories；
- 任意 H-view、replacement、shuffle、endpoint、mask、augmentation 或 K cache；
- 失败 attempt 和 recovery artifact；它们必须保留，但不是 successful formal denominator。

Stage 1 root 只有在 Stage 2 明确批准时才可 promotion 到 formal train，并且必须同时满足：协议语义与 raw action contract 未改变；按冻结方案补齐到 $R=3$／9 条轨迹；全部 raw、receipt、verifier、anchor、balance 与 leakage checks 重新通过；在 formal manifest 中显式标记 `promoted_from_pilot: true`。被 promotion 的轨迹计入 360，不能重复计数。任何 pilot root 永远不能冒充 untouched validation/test；未满足 promotion 条件的 pilot 只保留为 development，不进入正式分母。

### D3. 全局数据单位与不可破坏约束

#### D3.1 基本数据单位

完整 root group 为：

$$
\mathcal G_i=
\left(
o_i,s_i,
\left\{
\left(y_{i,j},\left\{A^+_{i,j,r}\right\}_{r=1}^{3}\right)
\right\}_{j=1}^{3}
\right)
$$

其中：

- $o_i$：root 唯一 current RGB bundle；
- $s_i$：root 唯一 current robot-state bundle；
- $y_{i,j}$：第 $j$ 个 verifier-backed structured program；
- $A^+_{i,j,r}$：同一 intent 的第 $r$ 条真实成功未来轨迹。

#### D3.2 一个精确 current 只能属于一个 root candidate set

正确扩展：

```text
一个 family template
→ 更换 object instances、角色、布局、活跃子集、干扰物、scene seed
→ 产生多个真正不同的 current/root
```

禁止扩展：

```text
同一张 current 图像
→ 先取 A/B/C 当一组
→ 再取 A/C/D 当第二组
→ 再取 B/D/E 当第三组
→ 伪装成多个独立 roots
```

这些组合统计上属于一个更大的 `super-root`。第一版硬规则：

> [!important] Exact-current rule
> **一个精确 current 只冻结一个三分支 candidate universe。完成该 root 的 9 条正式轨迹后，必须建立新的 scene/current，不能继续排列组合制造独立样本。**

#### D3.3 Same-current contract

同一 root 的 9 条轨迹必须共享：

- 字节级一致或按预注册容差一致的 current head／wrist RGB；
- 相同 current robot-state 白名单；
- 相同 object instances、object roles 和静态布局；
- 相同 base snapshot／canonical anchor bundle；
- 相同 candidate universe、candidate hash 和 task tree；
- 相同 split；
- 相同模型可见 current metadata。

每个 branch／retry 必须使用 **fresh local scene reconstruction + canonical anchor verification**。只恢复 pose 或在同一 scene 内倒带不足以清除 contact、sleep 与 solver history。

#### D3.4 Provisional candidate → feasibility audit → formal freeze

固定顺序：

```text
1. 生成 provisional scene/root specification
2. 生成三个 provisional structured programs
3. 分别完成 task feasibility / physical feasibility audit
4. 三个 provisional candidates 全部可行
5. 正式冻结 candidate universe、hash 与 observable/oracle task tree
6. 生成并冻结 canonical prefix / prefix contract
7. 才允许调用正式 planner 进行 rollout
```

- feasibility audit 之前，candidate 只能标记为 `provisional`，不能写入 formal frozen universe；
- 三个 candidate 任一 `task_feasible=false/unknown` 时，该 provisional root 不得进入 formal freeze；
- audit 通过后，candidate universe、task tree 和 prefix contract 才获得不可变版本与 hash；
- task／physical feasibility 与 planner solvability 必须分账；
- planner 成功不能反向定义 candidate 是否物理可行；
- 冻结后某 candidate planner 失败，禁止静默删 candidate；
- 必须按预注册预算重试、标记 root incomplete，或整组退出正式 balanced cohort；
- 失败 attempt、预算、planner family/config、recovery lineage 与 attrition 必须保留。

#### D3.5 两层 root specification：slot 先冻结，candidate 后冻结

为防止 feasibility audit 阶段无记录地反复重抽“容易场景”，root 规范拆成两个不可互换的 artifact。

##### D3.5-A. `planned_root_slot_spec`

所有 formal primary／reserve slots 必须在任何 formal feasibility audit 前冻结：

```yaml
root_slot_id:
family_id:
split: train | validation | test | inherit_failed_slot
layout_difficulty: clear | medium | crowded | inherit_failed_slot
scene_seed:
generator_version:
origin: fresh_formal | promoted_pilot | reserve
slot_rank:
slot_status: planned_pending_feasibility | reserve_pending_activation
```

- `root_slot_id` 一经分配不得复用；
- primary/promoted slots 必须填写具体 split/difficulty；reserve slots 固定为 `inherit_failed_slot`，激活时继承被替换 slot 的已冻结值；
- scene、object instances 与 provisional programs 必须由 `scene_seed + generator_version + slot fields` 确定性生成；
- feasibility fail 只能改变 `slot_status` 并追加 failure receipt，不能重新采 seed、换 difficulty 或覆盖 slot；
- `promoted_pilot` 必须额外保存 pilot raw/hash 与 promotion approval。

##### D3.5-B. `candidate_frozen_root_spec`

只有某个 planned slot 的确定性 scene 与三个 provisional programs 全部通过 task／physical feasibility 后，才允许依次冻结 candidate universe/task tree、生成 canonical prefix；两者 hash 都存在后，最终写入：

```yaml
root_slot_id:
object_instances:
object_roles:
visible_referring_expressions:
candidate_programs:
candidate_universe_hash:
task_tree_hash:
prefix_contract_hash:
candidate_freeze_status: frozen_active
feasibility_receipt_hashes:
```

`candidate_frozen_root_spec` 是 candidate/task-tree/prefix 三者都冻结后的 active-root seal；生成后才允许进入 formal planner rollout。它不能反向修改 `planned_root_slot_spec` 的 family、split、difficulty、seed 或 origin。

##### D3.5-C. Primary 与 reserve 的 Stage 2 状态

```text
40 primary planned slots：
  Stage 2 内按确定性规则生成、审计；
  Stage 2 seal 前必须形成 candidate_frozen_root_spec，
  或留下 feasibility_failed 证据并按 rank 激活 reserve 补足 active slots。

16 ordered reserve planned slots：
  Stage 2 只冻结 slot/seed/generator/family/rank 与继承规则；
  candidate_freeze_status = pending_activation；
  未激活时不得假装已有 object/candidate/hash。
```

reserve 激活时，按冻结 generator 生成 scene 与 provisional programs，重新走 feasibility → candidate freeze；形成 append-only activation/freeze receipt。Stage 2／3 的任何 slot failure 都必须进入：

```text
planned slot
→ feasibility pass / fail
→ fail reason
→ reserve activation rank
→ candidate freeze / second failure
```

每次 reserve activation 必须写 `activation/reserve_activation_receipt.json`：

```yaml
reserve_root_slot_id:
replaces_failed_root_slot_id:
reserve_rank:
resolved_split:
resolved_layout_difficulty:
failed_slot_terminal_receipt_hash:
activation_policy_version:
activation_timestamp:
activation_receipt_hash:
```

- 不修改 reserve 原始 `planned_root_slot_spec` 中的 `inherit_failed_slot`；
- resolved split/difficulty 只由 activation receipt 解析；
- reserve 的 `candidate_frozen_root_spec.activation_receipt_hash` 必须指向该 receipt；primary 使用 `not_applicable`；
- loader、finalizer 与 seal audit 必须从 planned primary spec 或 reserve activation receipt 解析 resolved split/difficulty，禁止现场猜测或回写原 planned spec。

### D4. 场景模板、物体数量与布局难度

#### D4.1 角色数量

| 类型 | 推荐／冻结范围 |
|---|---:|
| 当前 root 真正操作的物体 | 1～4 |
| 当前 root 的目标／工具／槽位 | 1～4 |
| 语义相关干扰物 | 1～2 |
| 非任务障碍／背景物体 | 0～1 |
| 总物体／设施 | 6～10 |

场景可以丰富，但每个 root 只能围绕一个明确变量分支：

- F1 只改变被选对象；
- F2 固定主对象，只改变目标／关系；
- F3 固定对象、V/H 次数和终态，只改变 V/H 顺序；
- F4 固定对象—槽位映射、子任务集合和终态，只改变子任务顺序。

#### D4.2 每个 family 的 10-root 难度配额

| 难度 | roots / family | 初始空间范围 |
|---|---:|---|
| 清晰 | 2 | 对象中心距离约 2.0～2.5 个图像投影物体宽度 |
| 中等靠近 | 6 | 约 1.5～2.0 个投影物体宽度 |
| 较难拥挤 | 2 | 约 1.2～1.5 个投影物体宽度，允许部分遮挡 |

距离只是 Stage 0/1 的初始工程范围。每个 root 最终必须同时满足：

- 每个 candidate object 有足够可见像素；
- current 中不存在无法从模型可见图像区分的完全遮挡目标；
- 夹爪可独立抓取每个活跃对象；
- 抓取一个对象不会推动邻近对象；
- 三个 candidate 均通过 physical feasibility audit；
- 三个 branch 均可在冻结预算内规划、执行和验证。

#### D4.3 原语复用边界

首批可复用 RoboTwin2 官方稳定的抓取、放置、摇动、sorting／ranking actor 与 primitive，但必须在一个联合受控 scene 中重新组合；禁止把多个官方 episode 直接拼接成一个 root。

以下任务留到第二批，不进入首批 360：

- 按铃／拨开关／订书机；
- 双臂交接或协作；
- 抽屉打开—取物—关闭；
- 堆叠与拆解；
- 工具使用。

原因是它们同时改变对象结构、接触方式、机械臂数量、轨迹长度和 success condition，会破坏首批的受控归因。

### D5. 每个 intent 的三种真实 realization

#### D5.1 固定组成

| realization | 必须保持不变 | 允许改变 | 主要用途 |
|---|---|---|---|
| `r_pc` | current、anchor、candidate program；三个 intent 复用同一 canonical prefix bytes/steps | 只允许在 `canonical_prefix_end` 之后按各 intent 分叉 | `prefix_controlled`；研究 $H/P$/compatible set/reveal |
| `r_inv_path` | current、anchor、同一 structured program、事件顺序、成功谓词、**执行臂**、250 Hz primary stream | 抓取角度、接近方向、运输弧线、waypoint、planner seed | 排除 canonical planner-path fingerprint |
| `r_inv_motion` | current、anchor、同一 structured program、事件顺序、成功谓词、**执行臂**、250 Hz primary stream | 速度、event physical duration、order-preserving time-warp、轻微停顿、合理幅度扰动；由此改变事件占用的 raw-step 数 | 验证同一运动学执行路径上的非语义 motion nuisance invariance |

三条都必须是真实执行并通过 verifier，禁止：

- 从同一 trajectory 复制后简单加噪；
- 通过重新采样 current 生成所谓 realization；
- 让 `r_inv` 改变 candidate program 或事件顺序；
- 在 `r_inv_motion` 中切换左右执行臂；
- 把 derived resampling 冒充真实 rollout 或改变 primary stream 的 250 Hz 采样率；
- 将 planner path／seed 暴露给模型；
- 把严格 $P$ 强加到两个 `r_inv`，导致真实 trajectory-invariance 被破坏。

#### D5.2 Cohort 归属

```text
prefix_controlled cohort
  = 三个 intent 的 r_pc

trajectory_invariance cohort(intent_j)
  = intent_j 的 r_pc + r_inv_path + r_inv_motion
```

严格 $P$ 只属于具体 `prefix_controlled` cohort。两个 `r_inv` 可具有不同数值路径；它们不参与严格 matched-$P$ 主曲线，除非另行建立并冻结新的 comparison cohort。

> [!note] 可选 `r_inv_arm` 诊断
> 左右臂切换会同时改变动作向量激活维度、运动学结构、抓取方向、规划空间和相机条件，因此只能作为单独的 `r_inv_arm` OOD／invariance diagnostic。它不计入首批固定 $R=3$，不能替代 `r_inv_path` 或 `r_inv_motion`，其 cohort、预算和 claim 必须另行预注册。

### D6. F1：近邻同类物体选择

#### D6.1 固定研究变量

- **固定**：公共目标容器、place relation、任务程序结构、current、anchor。
- **唯一分支变量**：被选择并搬运的具体同类对象 identity。
- **科学目标**：future action 必须与 current 中具体对象绑定，不能只读机械臂绝对去向。

#### D6.2 固定场景角色

| 角色 | 数量 | 要求 |
|---|---:|---|
| active same-class objects | 3 | 几何尺寸和抓取难度尽量一致；颜色／标记清晰 |
| common target container | 1 | 三个 candidate 共用同一目标 |
| similar distractors | 2 | 外形或类别与 active objects 相似，但不属于候选 |
| background obstacle/object | 1 | 不得阻断任一 candidate 的可行抓取 |
| 总数 | 约 7 | 满足对应 root 的清晰／中等／拥挤配额 |

典型实例：红／绿／蓝三个罐头，一个塑料盒，两个相似瓶罐干扰物，一个杯子或小障碍。

#### D6.3 固定三个 candidate programs

```text
F1-A：pick(red_can)   → place(red_can, inside, common_box)
F1-B：pick(green_can) → place(green_can, inside, common_box)
F1-C：pick(blue_can)  → place(blue_can, inside, common_box)
```

实际对象名称必须由 current 可解析的 canonical referring expression 生成，颜色只是示例；模型不得看到 simulator instance ID。

#### D6.4 Prefix contract

三个 `r_pc` 复用：

```text
arm initial pose
→ object-cluster 上方的公共预抓取区域
```

- `prefix_type = kinematic_shared_path`；
- `canonical_prefix_end` 位于朝具体对象发生可观测分叉之前；
- 禁止用 idle、padding 或无任务意义停顿延长 $P$；
- exact $P$、第一次数值 divergence 与 observable object-selection evidence 分开记录。

#### D6.5 跨 root 平衡

三个 active objects 的 identity 与绝对位置必须轮换，例如：

```text
root 1：红左 / 绿中 / 蓝右
root 2：蓝左 / 红中 / 绿右
root 3：绿左 / 蓝中 / 红右
```

10 个 roots 内：

- 每种 active identity 在左／中／右尽量均衡；
- active identity 不与 branch index、candidate position 或执行臂绑定；
- common target pose 可随 root 变化，但同一 root 内三个 candidate 共用；
- distractor identity 和位置随 scene seed 变化。

#### D6.6 F1 realization 要求

- `r_inv_path`：执行臂固定；改变接近方向、抓取角度或运输弧线，仍抓同一对象并放入公共容器；
- `r_inv_motion`：保持对象与关系，改变速度／time-warp／轻微停顿；
- 三条 realization 中，非目标 active objects 的移动量都必须低于 Stage 2 冻结阈值。

#### D6.7 F1 verifier

必须检查：

1. 抓取对象 identity 与 candidate program 一致；
2. 正确对象满足 `inside(common_box)`；
3. 两个非目标 active objects 基本不动；
4. distractors 与障碍物未发生超阈值位移；
5. 轨迹没有通过文件名、branch index 或固定手臂泄漏 intent。

#### D6.8 F1 root 进入正式 cohort 的条件

- 三个 active objects 在 current 中均可见、可区分、可独立抓取；
- 三个 candidate 全部物理可行；
- 9 条轨迹全部成功并通过 verifier；
- current/anchor equivalence 通过；
- 对象位置与 candidate/branch 顺序平衡审计通过。

### D7. F2：同一物体、不同目标—关系组合

#### D7.1 固定研究变量

- **固定**：主操作对象、current、anchor、共同抓取／运输前缀。
- **唯一分支变量**：绑定在一起的目标设施—关系组合 `box+IN / scale+ON / pot_or_stand+BESIDE`。
- **科学目标**：future 与 current 共同识别 object–target–relation program bundle，而不是只输出方向。
- **当前不能声称**：relation 与 facility 已经解耦，或 `inside/on/beside` 能跨新 reference facility 组合泛化。

#### D7.2 固定场景角色

| 角色 | 数量 | 要求 |
|---|---:|---|
| main object | 1 | 三个 candidate 操作同一实例 |
| target facilities | 3 | 分别支持 `IN`、`ON`、`BESIDE` |
| similar distractors | 2 | 不属于目标设施或主对象 |
| obstacle/background object | 1 | 不得使某个 candidate 独有地更难 |
| 总数 | 约 7 | 跨 root 更换实例与布局 |

典型实例：一个罐头、塑料盒、电子秤、锅／展示架、两个干扰物和一个小障碍。

#### D7.3 固定三个 candidate programs

```text
F2-A：pick(main_object) → place(main_object, inside, plastic_box)
F2-B：pick(main_object) → place(main_object, on, electronic_scale)
F2-C：pick(main_object) → place(main_object, beside, pot_or_stand)
```

candidate program 的语义关系名称仍使用冻结 ontology：`inside`、`on`、`beside`；不得用 left/right 代替语义关系。第一批中 facility 与 relation 一一绑定，因此主指标命名为 **object–target–relation bundle grounding**。

为避免几何谓词重叠，verifier 不直接把通用接触关系当作互斥真值，而冻结三个 family-specific success regions：

| Semantic relation | Verifier predicate | 必须满足的互斥条件 |
|---|---|---|
| `inside` | `inside_volume(subject, box)` | subject 的判定点／体积进入 box interior；不落入 top-surface-only 或 beside region |
| `on` | `top_surface_region(subject, scale)` | subject 位于 scale 顶面支持区域与高度带；不进入 inside volume 或 beside annulus |
| `beside` | `beside_annulus(subject, pot_or_stand)` | subject 位于 reference 周围冻结环带且不接触 top support／inside volume |

三个区域的几何范围、容差和优先级在 Stage 2 按统一 verifier version 冻结；test 后不得修改。

#### D7.4 Prefix contract

三个 `r_pc` 严格共享：

```text
approach main object
→ grasp complete
→ lift complete
→ transport to common intermediate pose
```

该前缀作为 verifier-backed 共同抓取／运输子任务保存；若 Stage 0/1 证明某段不能稳定逐 step 复用，必须在 Stage 2 缩短 canonical prefix，而不能用 padding 修补。

#### D7.5 目标位置平衡

10 个 roots 中，每种设施／关系在左／中／右区域出现约 3～4 次：

- box、scale、pot/stand 不能长期固定在左／中／右；
- relation 与绝对位置、执行臂、branch index、candidate display position 解耦；
- 主对象位置和实例跨 root 变化；
- F2 candidate 的路径长度与时长应尽量匹配，但不牺牲物理真实性。

#### D7.6 F2 realization 要求

- `r_inv_path`：执行臂固定；同一对象、同一关系，改变 approach／transport path／planner seed；
- `r_inv_motion`：同一程序，改变速度、order-preserving time-warp 或轻微停顿；
- 三条 realization 不能改变目标 facility 或 relation。

#### D7.7 F2 verifier

必须检查：

1. 操作的是正确 main object；
2. 满足 candidate 指定的目标 facility；
3. 满足预期 `inside_volume/top_surface_region/beside_annulus` 互斥区域谓词；
4. 另外两个 family-specific region predicates 不成立，其他目标设施未误满足等价 success；
5. distractors／障碍物无超阈值移动。

#### D7.8 F2 结论边界

F2 允许 endpoint-only 有一定效果。F2 可以支持 visual grounding、future replacement、目标—关系组合识别和 content-based $H/P$ reveal；不能据此声称 relation/facility 已解耦、关系组合泛化或动作顺序理解。

更强的 relation-crossed 版本可在后续让同一 reference facility 支持 `inside/on/beside`，或跨 root 交叉 relation 与 facility；它不属于首批 360，不能在当前数据上提前声称。

### D8. F3：相同起终态的细粒度动作顺序

#### D8.1 固定研究变量

- **固定**：同一瓶子、起点、终点、V/H 原语数量、动作原语 multiset、最终物体与机械臂状态。
- **唯一分支变量**：V/H 闭环动作原语的先后顺序。
- **科学目标**：模型必须使用 temporal order，不能只用 endpoint、统计量或事件计数。

#### D8.2 固定场景角色

| 角色 | 数量 | 要求 |
|---|---:|---|
| main bottle | 1 | 三个 candidate 操作同一实例 |
| original pad | 1 | 起点和最终放回位置 |
| similar bottle distractors | 2 | 外观相似但不参与任务 |
| central manipulation region | 1 | 所有闭环原语共同参考位姿 |
| ordinary distractors | 1～2 | 不得被误碰 |
| 总数 | 约 6～7 | current 中主瓶必须可区分 |

#### D8.3 闭环原语定义

```text
V：从 central pose 出发完成一次竖直 oscillation，并回到 central pose
H：从 central pose 出发完成一次水平 oscillation，并回到 central pose
```

首批坐标定义固定为：

```yaml
axis_frame: table
vertical_axis: z_table
horizontal_axis: x_table
oscillation_direction: symmetric_positive_negative_about_central_pose
```

- V 沿 table frame 的 $\pm z$ 完成闭环；
- H 沿 table frame 的 $\pm x$ 完成闭环；
- 抓取角度或 EEF orientation 变化不能改变 V/H 的物理轴定义；
- 若服务器审计证明 `x_table` 因场景边界不可行，必须在任何 Stage 0 轨迹前升级 protocol version，不能逐 root 静默改成 $y$ 轴。

每个原语必须具有：

- 预注册的主轴、最小幅度和最大偏轴分量；
- 明确的 start/end central-pose tolerance；
- 独立 event start/complete marker；
- 对 bottle grasp continuity 的检查；
- 相同的事件计数语义，不因时间采样率变化改变标签。

原语数值阈值在 Stage 1 根据可执行性估计，在 Stage 2 对 formal collection 一次性冻结；test 后不得修改。

#### D8.4 固定三个 candidate programs

```text
F3-A：V → V → H → H
F3-B：V → H → V → H
F3-C：V → H → H → V
```

三个程序必须同时满足：

- V 各 2 次、H 各 2 次；
- 总原语数相同；
- 起点相同、终点相同；
- 瓶子最终回 original pad；
- 机械臂最终回同一 rest pose；
- gripper final state 相同；
- 非任务物体最终状态等价；
- action steps、总时长和停顿模式近似匹配。

#### D8.5 Prefix contract

三个 `r_pc` 严格共享：

```text
grasp main bottle
→ lift
→ move to the same central pose
→ complete the same first V event
```

`canonical_prefix_end` 位于共同第一个 V 完成、重新回到 central pose 之后。共享前缀是可验证的共同抓取—抬升—居中—V 事件序列，禁止用 artificial idle 扩大 $P$。由此三个 full programs 具有更长的共同事件前缀，而不是让某个 candidate 在第一个事件就被唯一识别。

#### D8.6 F3 compatible set

```text
H ≤ P                    → {F3-A, F3-B, F3-C}
看到共同第一个 V         → {F3-A, F3-B, F3-C}
看到 V V                 → {F3-A}
看到 V H                 → {F3-B, F3-C}
看到 V H V               → {F3-B}
看到 V H H               → {F3-C}
```

短 $H$ 不能强行 one-hot。observable task-tree rule 只在模型可见 future-action prefix 提供相应事件证据后收缩集合。

#### D8.7 F3 realization 要求

- `r_inv_path`：执行臂固定；允许改变抓取角度、到 central pose 的路径与原语间的非语义连接路径；V/H 顺序和次数不变；
- `r_inv_motion`：执行臂与 250 Hz primary stream 不变；允许改变速度、event physical duration、order-preserving time-warp、合理幅度和轻微停顿，从而改变事件占用的 raw-step 数；V/H 顺序不变；
- 任何 derived resampling 只属于 order-preserving control，不是真实 `r_inv_motion` rollout；
- 所有 realization 必须满足同一 event detector／verifier，不得为每条轨迹单独调阈值。

#### D8.8 F3 verifier

必须检查：

1. 操作的是 main bottle；
2. V/H 各完成两次；
3. 实际事件顺序与 candidate program 完全一致；
4. 每个事件幅度达到冻结阈值，偏轴分量不过阈值；
5. 每个事件结束时回到 central-pose tolerance；
6. 中途 grasp continuity 成立；
7. bottle 最终回 original pad；
8. arm 回 rest pose，gripper state 一致；
9. 三个 branch 的 final-state equivalence 通过；
10. action steps、总时长和停顿规则通过 duration-matching Gate。

F3 verifier 的事件判定只使用隐藏审计流中的：

```text
realized EEF trajectory in table frame
bottle pose trajectory in table frame
grasp/contact continuity
```

模型输入仍使用 `controller_effective_setpoint_v1`，但 verifier 禁止因为 command／setpoint 名义上发出了 V/H 就判定成功；必须由 realized motion 证明幅度、主轴、闭环返回、grasp continuity 和实际顺序均成立。

#### D8.9 F3 必做强控制

##### D8.9-A. Valid temporal reorder：合法重排必须同步切换 target

F3 的 strict $P$ 已包含共同第一个 V，因此 valid reorder 必须保持整个 canonical prefix 不变，只重排 `canonical_prefix_end` 之后的三个 V/H suffix blocks。当 suffix 重排后恰好对应另一个冻结 candidate 时：

```text
固定 grasp → lift → central → shared-first-V prefix
→ 只重排后续三个 event blocks
→ target 同步切换为重排后对应的 candidate
```

例如：

```text
F3-A = [shared V] + V H H
重排 suffix 为    H V H
得到 F3-B = [shared V] + H V H

正确判定：prediction 必须从 F3-A switch 到 F3-B
```

主指标是 `temporal_reorder_prediction_switch_rate`，并对冻结 candidate universe 内所有预注册有向合法重排成对报告。这是 F3 最强的顺序证据，不能仍以原 candidate 为 target 只期待分数下降。

每个 F3 reorder view 必须保存：

```yaml
source_raw_hash:
source_event_spans:
fixed_prefix_hash:
permutation:
target_before:
target_after:
boundary_continuity_error:
boundary_tolerance_version:
control_status: valid_reorder | invalid_boundary_discontinuity
control_generator_version:
```

Stage 2 必须冻结：

```yaml
f3_reorder_boundary_tolerance_version:
max_position_target_jump:
max_velocity_target_jump:
max_gripper_command_jump:
max_jerk_proxy:
```

任一拼接边界超过阈值时：

```text
control_status = invalid_boundary_discontinuity
→ 不进入 temporal_reorder_prediction_switch_rate
→ 只保留为 control-generator failure／审计证据
```

禁止模型通过明显的 position/velocity/gripper/jerk 拼接跳变识别 reorder。

##### D8.9-B. Invalid/OOD shuffle：非候选重排不能强塞原 one-hot

当重排后的 V/H 顺序不属于 candidate universe：

- target 标记为 `none_of_frozen_candidates`，不能沿用原 candidate one-hot；
- 若模型具有预注册 reject／none head，评测 rejection accuracy；
- 若没有 reject head，只报告 predictive entropy、maximum candidate margin、energy/OOD score 或无监督表示诊断；
- invalid/OOD shuffle 不与 valid temporal-reorder switch rate 混成一个指标。

若模型在合法重排后仍坚持原 label，F3 不得标记 Temporal Identifiability pass。对 invalid/OOD reorder 高置信输出最近 candidate 只表示 OOD calibration／rejection 不足；除非模型预注册了 reject head 与独立 OOD Gate，否则它不否定合法 candidate 内的 Temporal Identifiability。

### D9. F4：共同子任务后的高层操作顺序

#### D9.1 固定研究变量

- **固定**：对象集合、object-slot 映射、公共第一子任务、后续子任务集合、放置次数和最终世界状态。
- **唯一分支变量**：A/B/C 三个 place 子任务的完成顺序。
- **科学目标**：识别高层 structured program order，而不是 final state 或 bag-of-subtasks。

#### D9.2 固定场景角色

| 角色 | 数量 | 要求 |
|---|---:|---|
| common-prefix object X | 1 | 所有 candidate 首先操作 |
| ordered objects A/B/C | 3 | 三者各有固定目标槽 |
| target slots A/B/C | 3 | object-slot 映射在同一 root 内固定 |
| common-prefix target tray | 1 | X 的公共目标 |
| distractors | 1～2 | 不参与任务且不得超阈值移动 |
| 总数 | 9～10 | 满足该 root 难度配额 |

典型实例：白色方块 X，红／绿／蓝三个罐头 A/B/C，三个固定目标槽，一个公共托盘和两个干扰物。

#### D9.3 固定公共语义前缀

所有 `r_pc` 首先完成：

```text
place(common_object_X, inside, common_start_tray)
```

- 这是完整、可验证的公共子任务；
- `prefix_type = shared_semantic_subtask`；
- `canonical_prefix_end` 位于 X 的 success predicate 首次稳定成立之后、A/B/C 第一个子任务开始之前；
- 禁止用等待、padding 或中性绕路扩展 $P$。

#### D9.4 固定三个 candidate program 模板

```text
F4-P1：common_X → A → B → C
F4-P2：common_X → A → C → B
F4-P3：common_X → B → A → C
```

其中：

```text
A = place(object_A, target_slot_A)
B = place(object_B, target_slot_B)
C = place(object_C, target_slot_C)
```

P1/P2 共享第一个分支子任务 A，必须看到第二个分支子任务才能完全区分；P3 在第一个分支子任务即与它们区分。禁止使用 `ABC / BCA / CAB` 这类第一个对象就全部分开的循环模板作为首批主程序。

#### D9.5 F4 compatible set

```text
H ≤ P / 只完成 common X：
  {F4-P1, F4-P2, F4-P3}

看到第一个分支子任务 A：
  {F4-P1, F4-P2}

看到第一个分支子任务 B：
  {F4-P3}

看到 A → B：
  {F4-P1}

看到 A → C：
  {F4-P2}
```

compatible set 只在对应 `place(object, slot)` completion event 被 observable rule 确认后收缩；不能因 planner phase、文件名或 hidden object state 提前收缩。

#### D9.6 Branch-neutral block contract

为了让 A/B/C 子任务可以在不制造边界 jerk 的情况下比较或重排，每个 block 必须设计为：

```text
branch_neutral_pose
→ grasp object_i
→ place object_i into slot_i
→ release
→ return to the same branch_neutral_pose
```

每个 block 保存并验证：

```yaml
block_id:
object_role:
target_slot_role:
start_neutral_pose_hash:
end_neutral_pose_hash:
start_gripper_state:
end_gripper_state:
start_arm_velocity_tolerance:
end_arm_velocity_tolerance:
precondition_predicates:
postcondition_predicates:
raw_event_span:
block_action_hash:
```

硬要求：

- block 开始／结束的 arm pose、velocity 与 gripper state 在冻结 tolerance 内一致；
- 已完成的 object-slot placement 不阻塞后续 block；
- block 只改变自己的 object-slot predicate，不破坏先前完成的 predicates；
- block boundary action continuity、position/velocity jump 与 jerk proxy 通过；
- 任何人工 splice 必须在 fresh scene 中 replay 并通过完整 F4 verifier，不能只做数组拼接。

#### D9.7 跨 root 对象—符号置换

A/B/C 是 root-local 角色，不是永久 object identity。每个 root 必须重新冻结 `role_symbol → visible object → target slot` 映射，并满足：

- 不同 root 轮换哪个 visible object 充当 A/B/C；
- P1/P2/P3 不与 local intent ID 或 candidate display position固定绑定；
- 开始对象 identity 在全 family 中尽量平衡；
- object/slot 的左／中／右位置尽量平衡；
- 实际 10-root role schedule、scene seed 和 candidate display permutation 在 Stage 2 写入 formal manifest 后冻结。

#### D9.8 F4 realization 要求

- `r_inv_path`：执行臂固定；每个 place 子任务允许不同抓取角度、transport path、waypoint 或 planner seed；子任务完成顺序不变；
- `r_inv_motion`：允许速度／time-warp／轻微停顿变化；子任务顺序和 object-slot mapping 不变；
- 三种 realization 都必须先完成 common X subtask，再执行正确 A/B/C 序列。

#### D9.9 F4 verifier

必须检查：

1. common X subtask 首先完成；
2. X 在公共托盘中稳定满足 success predicate；
3. A/B/C 最终都进入各自 slot；
4. 记录三个 `place(object, slot)` 的完成时间；completion 定义为“release 后，对应 slot predicate 第一次连续稳定满足 `completion_stability_frames` 帧的首帧”；
5. 完成时间诱导的顺序与 candidate program 完全一致；
6. 三个 branch 的最终 object poses、arm poses、gripper state 和非任务物体状态等价；
7. action steps、总时长和停顿模式近似匹配；
8. 无目标对象或 distractor 未被意外移动。

若任意相邻 completion times 的差小于 Stage 2 冻结的 `completion_tie_tolerance`，该 trajectory 标记 `failed_order_tie`，不能用浮点时间强行排序或进入顺序标签。

#### D9.10 F4 valid program replacement 与 strict block reorder

##### D9.10-A. 真实分支 program replacement（必做）

```text
P1 的真实成功 future
→ 替换为同 root 的 P2/P3 真实成功 future
→ target 同步切换
```

该控制命名为 `f4_real_branch_program_replacement`。它证明模型服从另一个合法 program，但不声称“相同 action blocks 只改变顺序”。

##### D9.10-B. Strict neutral-to-neutral block reorder（条件式强控制）

只有 [[#D9.6 Branch-neutral block contract]] 全部通过时，才允许：

```text
固定 common-X canonical prefix
→ 提取同一 source set 的 neutral-to-neutral A/B/C blocks
→ 只排列 A/B/C block 顺序
→ target 切换到重排后对应的 candidate
→ fresh-scene replay + full verifier
```

每个 derived/replayed view 必须保存：

```yaml
source_raw_hashes:
source_block_hashes:
source_event_spans:
permutation:
target_before:
target_after:
boundary_continuity_error:
splice_replay_receipt_hash:
control_generator_version:
```

若 neutral boundary、world precondition、action continuity 或 replay verifier 任一失败，标记 `strict_block_reorder_not_available`，禁止把直接数组 splice 当作 valid control；此时 F4 只使用真实分支 replacement，并把 strict block reorder 报为未实现／不适用。

#### D9.11 F4 两层证据状态与 claim 上限

`f4_natural_sequence_dependence_pass` 至少要求：

- natural future 稳定优于 endpoint-only；
- action multiset/statistics-only 不能完成任务；
- 参数量与预算匹配的 order-aware encoder 优于 order-insensitive set encoder；
- `f4_real_branch_program_replacement` 正确 prediction-switch；
- same-intent `r_inv_path/r_inv_motion` 保持；
- planner ID、length、padding、branch index 不能确定性解码。

它最多支持：

> 模型在自然真实轨迹上使用了与高层操作顺序相关的证据。

`f4_strict_block_order_intervention_pass` 在上述基础上额外要求：

- neutral-to-neutral A/B/C block contract 全部通过；
- 固定 common-X prefix 与 block 内容，只交换 block 顺序；
- boundary continuity 通过；
- fresh-scene replay 通过完整 verifier；
- target 随重排后的合法 program 正确切换。

只有它才能支持：

> 在保持 block 内容基本不变时，仅改变 block 顺序就会使预测正确切换。

全局 `temporal_identifiability_pass` 保留；F4 必须同时报告上述两个子状态。没有 strict block reorder 时，不得把 natural-sequence 证据升级成严格 block-order intervention claim。

#### D9.12 F4 root 进入正式 cohort 的条件

- common prefix 可独立验证并逐 branch 复现；
- 三个 candidate 全部可行，且 object-slot final state 相同；
- 9 条轨迹均通过顺序 verifier；
- completion stability 与 tie Gate 通过；
- endpoint-only 和 final-state classifier 在 pilot 中不能形成确定性标签；
- subtask count、trajectory length、planner ID 和 branch index probe 不得形成确定性 shortcut。

#### D12.4 Root accepted 的必要条件

- root spec、scene seed、family、split 与 candidate universe 已冻结；

#### D12.5 Incomplete root 与预注册 reserve replacement

Stage 2 不只冻结 40 个 primary planned slots，还必须冻结：

```text
40 primary planned_root_slot_spec
+ 4 ordered reserve planned_root_slot_spec / family
= 56 planned slots in total
```

16 个 reserve slots 不属于 formal accepted denominator；只有替换失败 active slot 后才可能成为 attempted/accepted root。Stage 2 时它们没有 object/candidate/task-tree/prefix hash，并固定：

```yaml
reserve_family_id:
reserve_rank: 1 | 2 | 3 | 4
scene_seed:
deterministic_scene_generator_version:
replacement_policy: inherit_failed_slot_split_and_layout_difficulty
candidate_freeze_status: pending_activation
```

固定替换规则：

```text
primary root 达到预注册 stop condition 仍 incomplete
→ 保留全部 raw / attempt / receipt / verifier / failure evidence
→ 锁定该 primary slot 的 family、split 与 layout_difficulty
→ 按 reserve_rank 启用该 family 下一个未使用 reserve slot
→ 继承失败 slot 的 split/difficulty
→ 用冻结 seed + generator 生成 provisional scene/programs
→ 重新执行 feasibility audit → candidate freeze → collection
```

禁止：

- 人工挑选“看起来更容易成功”的 reserve；
- 先试多个 reserve，再只保留成功者；
- 用 reserve 覆盖失败 primary 的 ID 或删除其证据；
- 四个 reserve 耗尽后临时增加新 root 而不升级 manifest／获得批准。

若某 family 的 4 个 reserve 全部耗尽仍不足 10 个 accepted roots，则该 dataset 状态为 `formal_dataset_incomplete`，停止 seal 并报告用户。

最终报告必须分开给出：

```text
planned primary slots
planned reserve slots
attempted roots
accepted roots
incomplete roots
reserve activations by rank
family-level attrition rate
failure-reason distribution
```

### D13. 防捷径平衡与 leakage probes

#### D13.1 全局平衡要求

1. **空间位置**：对象、目标和 intent 在左／中／右、近／中／远尽量均衡。
2. **执行臂**：不能出现某 intent 永远由某一手臂执行；物理可行时跨 root 平衡。
3. **长度与时长**：F3/F4 原语／子任务数相同；总 action steps 和 duration 初始目标约在 $\pm10\%$ 内，正式阈值 Stage 2 冻结。
4. **branch 保存顺序**：branch index 与 intent/program 不固定映射。
5. **candidate 显示顺序**：每次随机排序，做 permutation consistency test。
6. **对象角色**：同类对象跨 root 不得永久充当主对象、目标或 distractor 中的固定角色。
7. **文本与程序统计**：candidate 长度、op 频率、constraint 比例和模板形态平衡或显式审计。

#### D13.2 必做 leakage probes

```text
candidate-only
branch/file-name-only audit
planner-ID probe
trajectory-length probe
padding / pause-pattern probe
event-count probe
action multiset / statistics-only
endpoint-only
no-vision
future-only / no-current
wrong-scene future
instruction-only
candidate permutation / cycle
```

若 branch ID、candidate position、planner ID、length、padding 或静态 endpoint 能确定性解码 F3/F4 label，则对应 root/family 不能支持 temporal claim，必须在 formal collection 前修复或退出。

#### D13.3 Controls 的正确预期

| Control 类型 | 示例 | 预期 |
|---|---|---|
| valid temporal reorder | event blocks 重排后对应另一个合法 candidate | target 同步切换；测 prediction-switch |
| invalid/OOD temporal shuffle | reverse／shuffle 后不属于 candidate universe | 测 reject、entropy、margin 或 OOD score；不使用原 one-hot |
| order-preserving nuisance | time-warp、速度缩放、保持事件顺序的重采样 | structured intent 应保持 |
| information deletion | endpoint-only、event-drop、局部遮挡 | 删除关键过程信息后应下降 |
| valid replacement | 同 root 换成另一真实 future，并同步切换 target | 在 singleton-eligible $H$ 上预测应正确切换 |

`wrong-scene future` 也必须在生成 derived control 时分账：

- 若 transplanted future 在当前 scene 中仍可按 observable rules 映射到 candidate universe 的合法程序，使用对应合法 target；
- 若 future 与当前 objects／targets／kinematics 不兼容，标记 `scene_incompatible_ood`，只使用 reject／entropy／margin／OOD 指标；
- 禁止给 scene-incompatible future 强塞原 scene 的 one-hot label，并把分数下降与合法 replacement switch 混为一个指标。

`no-vision` 的 Gate 按 family 分开：F1/F2/F4 要求它相对完整输入明显下降，以证明 current grounding；F3 只把它作为诊断，不构成失败条件，因为 V/H 顺序本身可能足以识别程序。

### D14. Root-aware sampler 与正式 split

#### D14.1 普通训练 batch

same-current 是数据构造方式，不表示同一 batch 同时放入同 root 的多个 branch。

硬规则：

```text
一个普通训练 batch 中，每个 root 最多出现一个样本
```

允许：

```text
root_001 / F1 / intent B / r_inv_path
root_014 / F2 / intent A / r_pc
root_023 / F3 / intent C / r_inv_motion
root_037 / F4 / intent B / r_pc
```

禁止同 batch：

```text
root_001 / intent A
root_001 / intent B
root_001 / intent C
```

不同 epoch 轮换同一 root 的 branch、realization 和 H-view。replacement 在评测时成对运行，不要求进入同一普通训练 batch。

#### D14.2 正式 split

每个 family 10 roots：

```text
5 train / 2 validation / 3 test
```

| Split | roots | formal raw trajectories |
|---|---:|---:|
| Train | 20 | 180 |
| Validation | 8 | 72 |
| Test | 12 | 108 |
| **总计** | **40** | **360** |

每个 family 的 `split × layout_difficulty` 固定配额为：

| Split | clear | medium | crowded | 合计 |
|---|---:|---:|---:|---:|
| Train | 1 | 3 | 1 | 5 |
| Validation | 0 | 2 | 0 | 2 |
| Test | 1 | 1 | 1 | 3 |
| **每 family 合计** | **2** | **6** | **2** | **10** |

这样 test 不会恰好全是 clear 或全是 crowded，同时维持每 family 的 2/6/2 总难度配额。

#### D14.3 Split 原子性

同一个 root 的以下内容必须同 split：

- 3 intents 与 9 raw trajectories；
- 所有 realization/cohort；
- 全部 H-view、replacement、shuffle、endpoint、mask 和 augmentation；
- current views 与 K cache；
- derived event views。

近重复 layout／scene family 必要时按更保守 `super-root` 原子划分。禁止逐 trajectory 或逐 derived row 随机 split。

#### D14.4 Test 隔离

test roots 不参与：

- normalization 拟合；
- action representation 选择；
- feature/encoder 选择；
- hyperparameter 与 checkpoint 选择；
- compatible-set rule 调整；
- verifier threshold 与 final-state tolerance 修改。

任何被人工查看或用于修改协议的 root 立即失去 untouched test 身份。

> [!warning] Phase-1 结论边界
> 本 split 服务于 `phase-1 formal mechanism dataset`。即使每 family 有 3 个 test roots，也只支持首轮独立场景机制证据，不足以单独承担强 task-family generalization claim；Temporal Gate 通过后仍应追加新的独立 test roots／scene families 做确认。

### D16. 单个 root 的固定采集流程

```text
1. 读取已冻结的 planned_root_slot_spec；不得现场重采 slot/seed/split/difficulty
2. 用 scene_seed + generator_version 确定性生成 scene、object instances、roles、targets、distractors
3. 完成位置、角色、执行臂和长度平衡预检查并写 receipt
4. 生成三个 provisional structured candidate programs
5. 独立审计三个 candidate 的 task/physical feasibility
6. 任一失败：标记 slot feasibility_failed、保留原因、按 reserve rank 激活下一 slot；当前 slot 停止
7. 三个全部可行：冻结 candidate universe/hash、observable/oracle task tree，并写 candidate-freeze receipt
8. 生成并冻结 canonical prefix / prefix contract / hashes
9. 汇总 feasibility/candidate/task-tree/prefix hashes，最终写 candidate_frozen_root_spec
10. 只有 candidate_freeze_status=frozen_active 才允许进入 formal collection
11. 每个 branch 使用 fresh-scene reconstruction 恢复 canonical anchor
12. 采集三个 intent 的 r_pc
13. 采集三个 intent 的 r_inv_path
14. 采集三个 intent 的 r_inv_motion
15. 每次 attempt 立即写 terminal status、receipt 与 recovery lineage
16. 运行 family-specific verifier
17. 运行 current hash、anchor equivalence、duration 与 leakage checks
18. F3/F4 运行 final-state-equivalence verifier
19. 9 条全部通过后才标记 root accepted
20. root 封存后离线生成 H/replacement/reorder/OOD/endpoint derived views
21. finalizer 核对 slot、candidate freeze、reservation、attempt terminal、receipt、verifier、fresh-scene lifecycle 与 orphan
```

任何步骤失败都不得跳过后继续把部分数据标成正式 accepted root。

`pilot_attempt_budget_v0` 只服务 smoke/pilot；根据 pilot 证据，Stage 2 另行冻结 `formal_attempt_budget_v1`。二者不得共用同一个可事后扩大的计数器，也不能因 pilot 困难而暗增 formal budget。

#### D17.1 Stage 0：12 条 smoke

```text
每个 family 先建立 Pilot root A
→ 只采该 root 的 3 个 r_pc

4 families × 3 r_pc = 12 trajectories
```

只检查：

- scene 能否稳定创建；
- 三个 candidate 是否都可规划；
- canonical current/anchor 是否一致；
- family verifier 是否能区分成功／错误程序；
- 视频与物理行为是否合理。

Stage 0 不作 temporal 或 generalization claim。它是 Stage 1 累积 48 条中的前 12 条，不是额外数据批次；Stage 0 通过后，沿用同一批 pilot roots 继续补采 Stage 1 剩余 36 条。

#### D17.2 Stage 1：48 条 mechanism pilot

```text
每个 family：

Pilot root A：
  3 intents × (r_pc + r_inv_path) = 6

Pilot root B：
  3 intents × (r_pc + r_inv_motion) = 6

每 family 12 条 × 4 families = 48 trajectories
```

计数关系：

```text
Stage 0 已完成 Pilot root A 的 3 r_pc / family = 12
Stage 1 继续补：
  Pilot root A 的 3 r_inv_path / family = 12
  Pilot root B 的 3 r_pc + 3 r_inv_motion / family = 24
继续补采总数 = 36

累计 pilot 总量 = 12 + 36 = 48，而不是 60
```

必须裁决：

- F3/F4 endpoint-only 是否困难；
- F3/F4 event-block shuffle 是否破坏 label；
- trajectory length、padding、pause、planner ID 是否泄漏；
- object/target position 是否泄漏；
- Pilot root A 上的 same-intent path variation 是否保持语义；
- Pilot root B 上的 same-intent motion variation 是否保持语义；
- observable compatible set 是否按预注册事件收缩；
- verifier threshold 是否稳定且 family 内统一。

所有被查看的 Stage 1 roots 默认只算 development。只有满足 [[#D2.3 默认不计入正式 360 的数据]] 的 promotion 条件并在 Stage 2 manifest 中预先声明，才可补齐后进入 formal train；永远不得进入 validation/test。

### D18. 评测矩阵与科学 Gate

#### D18.1 主要对照

| 对照 | F1 | F2 | F3 | F4 |
|---|---|---|---|---|
| current-only／$H=0$ | 接近三候选随机基线 | 接近三候选随机基线 | 接近三候选随机基线 | 接近三候选随机基线 |
| correct future | 明显提高 | 明显提高 | 明显提高 | 明显提高 |
| valid future replacement | target switch | target switch | target switch | target switch |
| same-intent realization | 保持 | 保持 | 保持 | 保持 |
| no vision | **应明显下降；hard grounding Gate** | **应明显下降；hard grounding Gate** | 仅诊断；可保持高分 | **应明显下降；hard grounding Gate** |
| endpoint-only | 应较弱 | 允许部分效果 | 应明显失败 | 应明显失败 |
| valid temporal reorder | 非主 Gate | 非主 Gate | fixed-prefix suffix reorder 后 target switch | real-branch program replacement 必做；strict neutral-block reorder 可用时另报 |
| invalid/OOD shuffle | entropy/margin/reject 诊断 | entropy/margin/reject 诊断 | entropy/margin/reject 诊断 | entropy/margin/reject 诊断 |
| action multiset/statistics-only | 可能部分有效 | 可能部分有效 | 应接近失败 | 应接近失败 |
| wrong-scene compatible replacement | 合法 target | 合法 target | 按映射合法 target | 合法 target |
| scene-incompatible OOD future | reject/OOD 诊断 | reject/OOD 诊断 | reject/OOD 诊断 | reject/OOD 诊断 |
| candidate permutation | 结果一致 | 结果一致 | 结果一致 | 结果一致 |

#### D18.2 Future-content Gate

至少要求：

- correct future 相对 current-only 提供增量；
- replacement 在 singleton-eligible $H$ 上使预测正确切换；
- same-intent `r_inv_path/r_inv_motion` 保持语义；
- F1/F2/F4 的 no-vision 相对完整输入明显下降，证明 current grounding 必要；
- F3 的 no-vision 仅报告，不作为失败条件；其核心是 natural/valid reorder/invalid OOD 的顺序语义；
- wrong-scene control 按 compatible valid target 与 scene-incompatible OOD 分账；
- candidate permutation/cycle 通过。

#### D18.3 F3/F4 Temporal Identifiability Gate

只有同时满足以下条件才可 `temporal_identifiability_pass = true`：

1. natural future 稳定优于 endpoint-only；
2. action multiset/statistics-only 不能完成任务；
3. 合法 program-order 变化后预测切换到新的合法 target：F3 使用 fixed-prefix suffix-block reorder；F4 至少使用真实分支 program replacement，strict neutral-block reorder 可用时另报；
4. time-warp、速度缩放和 order-preserving resampling 保持语义；
5. planner ID、length、padding、branch index 不能确定性解码；
6. 结果跨独立 roots、预注册 seeds 与固定 checkpoint rule 稳定；
7. 不挑 seed、checkpoint、root 或 secondary metric；
8. observable compatible-set 与 singleton eligibility 规则在 test 前冻结。

#### D18.4 OOD robustness diagnostic／独立可选 Gate

invalid/OOD reorder 不属于 `temporal_identifiability_pass` 的必要条件。若 scorer 只能在三个 candidates 中强制选择，即使它完美理解合法顺序，也可能高置信输出最近 candidate；这反映 OOD calibration，不否定 candidate 内顺序理解。

- 未设计 reject head：只报告 entropy、maximum margin、energy/OOD score 与 nearest-candidate distribution；
- 明确预注册 `none-of-candidates/reject` head：可另立 `ood_rejection_gate`，冻结 OOD dataset、threshold 与 metric；
- `ood_rejection_gate` 与 `temporal_identifiability_pass` 分开命名、分开报告，任一不自动替代另一项。

#### D18.5 Claim 映射

| 通过什么 | 最多可以说什么 | 仍不能说什么 |
|---|---|---|
| F1 future-content Gate | future content 支持具体对象 grounding | 不代表时间顺序理解 |
| F2 future-content Gate | future content 支持 object–target–relation bundle grounding | 不代表 relation/facility 解耦、组合泛化或时间顺序理解 |
| F3 Temporal Gate | 模型在该 family 上依赖细粒度 V/H 顺序 | 不自动外推到高层程序 |
| F4 natural sequence dependence | 模型在自然真实轨迹上使用了与高层操作顺序相关的证据 | 不等于相同 blocks 的严格顺序干预，也不自动等于开放泛化 |
| F4 strict block-order intervention | 保持 block 内容基本不变、只改变顺序会使预测正确切换 | 不自动等于开放任务泛化或 policy 提升 |
| anchor-based H/P Gate | 特定 family/model/metric 下的 reveal curve | 不共享一个全局裸 $H_{reveal}$ |
| 后续 compression Gate | 固定 $H/P$/cohort 下的语义保真 | 不代表 policy rollout 改善 |
| policy multi-seed rollout | 相同部署输入下的控制效果 | 不能由 probe accuracy 替代 |

### D19. 当前停止线与变更控制

#### D19.1 当前不启动

F3/F4 通过 Temporal Identifiability 前，不启动或宣称：

- $K$-token compression 已有科学依据；
- FAST／DCT 与 K-query 的正式大规模比较；
- π0.5 联合训练；
- teacher–student／deployment-path alignment；
- policy rollout 提升；
- clean 750、randomized 7,500 或更大规模放量；
- 动作顺序理解、长程序语义压缩或正式 $H_{reveal}$ 已成立。

固定研究顺序：

```text
future content
→ task-conditioned temporal identifiability
→ anchor-based H/P
→ K / semantic compression
→ policy transfer
```

> [!important] 360 条的职责边界
> 本文的 360 条只构成 `phase-1 formal mechanism dataset`，用于 future-content、Temporal Identifiability 与 anchor-based $H/P$。模型、representation、H sampling、normalization、checkpoint、seeds、统计和 test seal 只在 [[#第二部分：F1–F4 机制模型训练与评测协议（Deferred）|独立机制训练评测规范]] 中设计。它也不是 RoboTwin2 官方 50 任务的完整多任务 policy 数据集；policy/intent mixing、官方 episode sampler、structured-program tokenization 或 π0.5 loader 只在 [[#第三部分：多任务训练混合与 π0.5 接入协议（Deferred）|独立 π0.5 接入规范]] 中设计。禁止由实现者临时猜测。

#### D19.2 需要版本升级的变更

以下任一改变都必须先报告影响、获得批准、升级 `design_version` 或相应 protocol version，并说明已有数据如何处理：

- 增删 F1–F4 family；
- 改每 family root 数、每 root intent 数或 $R$；
- 改 F3/F4 candidate program；
- 改 split 或 super-root 规则；
- 改 primary action stream／frequency／dimension；
- 改 task tree／compatible-set evidence rule；
- 改 verifier semantics、threshold 或 final-state tolerance；
- 改 attempt/query budget 或停止条件；
- 将 pilot root promotion 为 formal train，或试图将任何 pilot root 放入 validation/test；
- 改模型可见／不可见字段。

#### D19.3 不需要改变设计版本的内容

在不改变语义、分母、split 和 Gate 的前提下，下列内容可只升级实现版本：

- collector bug fix；
- receipt 字段补充；
- 性能优化；
- 不改变 raw semantics 的可重建 derived view；
- 便阅视频／可视化输出。

旧 artifact 必须保持不可变，新实现使用新 namespace/version。

### P3. 未来必须冻结的问题

正式版本至少要回答：

| 主题 | 必须冻结的内容 |
|---|---|
| 数据组成 | 官方 50-task trajectories、F1–F4 controlled roots 与其他数据源的职责和版本 |
| Sampler | 各数据源／task family／root 的采样权重；root-aware 与 ordinary episode sampler 怎样共存 |
| Batch | policy samples、intent samples、H-view samples 的 batch 组成与同-current 约束 |
| Loss | $\mathcal L_{policy}$、$\mathcal L_{intent}$、alignment／control losses 的权重和调度 |
| H-view | 离线缓存还是在线采样；family/cohort/H 的分布 |
| Program encoding | structured program 的 tokenization、candidate ranking 与 global decoding 接口 |
| Loader | π0.5 读取 raw／derived 的哪些文件、mask、timestamp、normalization 与 action schema |
| Ordinary episodes | 没有 same-current group 的官方 episode 如何参加 policy loss，是否参加 intent loss |
| Shared parameters | intent loss 实际更新哪些部署保留参数；future-only path 如何避免无法迁移 |
| Controls | policy-only、无 future semantic baselines、shared-no-alignment、teacher alignment、wrong/shuffled future、nonsemantic auxiliary |
| Budget | data amount、steps、seeds、parameters、compute、checkpoint rule 与 early stopping |
| Evaluation | 相同部署输入和预算下的多种子 rollout、cluster-aware statistics 与失败条件 |
