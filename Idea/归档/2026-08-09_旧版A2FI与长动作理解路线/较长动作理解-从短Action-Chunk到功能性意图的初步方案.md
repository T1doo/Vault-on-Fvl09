# 较长动作理解：怎样让模型从短 Action Chunk 看懂一段完整行为

> 整理日期：2026-07-27<br>
> 文档性质：围绕师哥问题形成的**初步方案讨论稿**<br>
> 适合读者：默认不了解机器人、机器学习和 VLA<br>
> 相关主线：[idea 主干](idea主干-动作序列的功能性意图理解.md) · [完整小白详解](idea1-小白详解-从动作序列到功能性意图A2FI.md)

## 0. 师哥提出的问题是什么

机器人策略通常不会一次性输出完成整项任务的所有动作，而是每次只预测一小段动作，也就是 **action chunk**。

例如，“把杯子放进柜子”可能实际需要：

```text
第 1 个 chunk：机械臂向杯子靠近
第 2 个 chunk：调整夹爪位置
第 3 个 chunk：闭合夹爪
第 4 个 chunk：把杯子抬起来
第 5 个 chunk：向柜子移动
第 6 个 chunk：把杯子伸进柜子
第 7 个 chunk：松开夹爪
```

单独看其中任意一个短 chunk，通常只能看出非常局部的运动。

因此师哥的问题可以重新表述为：

> 模型每次只处理很短的动作片段，那么它怎样把许多短片段联系起来，理解一段较长行为最终完成了什么、又是为了什么？

师哥还提出了一个候选办法：

> 能不能直接计算较长时间内的“累计变化”，再把这个累计变化告诉模型？

这份文档专门回答这两个问题。

---

## 1. 先给结论

我的初步答案是：

> **不要强迫控制模型一次输出特别长的 action chunk，也不要只把一长串动作压缩成一个累计位移。应该把“短时控制”和“长时理解”分成两条不同时间尺度的通路。**

整体结构可以先想成：

```text
控制通路：
当前观察
→ 预测一个短 action chunk
→ 执行其中一部分
→ 重新观察
→ 再预测下一个短 chunk

理解通路：
保存多个已经真实执行过的短 chunk
→ 保留它们的先后顺序
→ 识别“接近、抓住、抬起、搬运、释放”等事件
→ 把多个事件组合成子目标
→ 判断这个子目标在整项任务中的功能
```

一句更简单的话：

> 控制仍然“小步快走”，理解则负责“回头总结这一连串小步共同做成了什么”。

---

## 2. 为什么不直接让模型一次预测很长的动作

### 2.1 短 chunk 不是缺点

假设机器人一次预测未来 300 步动作。

如果第 20 步抓杯子时偏了两厘米，那么：

- 第 21 步以后的动作都基于“已经抓住杯子”；
- 但现实里杯子其实没抓住；
- 后面 280 步很可能全部失效。

短 chunk 可以让机器人不断重复：

```text
看一下
→ 动一小段
→ 再看一下
→ 根据真实结果纠正
```

这叫**闭环控制**。<br>
“闭环”的意思是：机器人执行后会重新读取真实环境，而不是按照最初计划蒙着头做到底。

所以本方案不准备为了“长动作理解”而破坏短 chunk 控制。

### 2.2 控制长度和理解长度不是一回事

这是整个问题最重要的区分：

| 概念 | 它关心什么 | 合适的时间长度 |
|---|---|---|
| 控制时间单位 | 下一小段机械臂应该怎么动 | 短 |
| 事件时间单位 | 是否完成一次抓取、释放或开门 | 中等 |
| 语义时间单位 | 这一串事件完成了哪个子目标、服务于哪个任务 | 长 |

模型完全可以：

- 每次只预测 10–50 步动作；
- 同时保存过去几百步已经执行的动作；
- 在更长历史上判断子目标和意图。

因此，“action chunk 很短”不等于“模型只能理解很短的行为”。

---

## 3. 另一个关键点：只能记录真正执行过的动作

模型预测的动作和机器人实际执行的动作不一定完全相同。

例如：

```text
模型预测了 40 步 action chunk
机器人只执行前 10 步
系统获得新画面后重新规划
剩下 30 步被丢弃
```

理解分支只能把前 10 步记入历史。

不能把完整 40 步都当作“已经发生的事实”，因为后 30 步只是一份被取消的计划。

因此需要明确区分：

```text
predicted actions：模型原先打算做什么
executed actions：机器人实际上做了什么
```

本 Idea 的主输入应该是 **executed actions，也就是已执行动作**。

这也是为什么理解分支需要一个专门的执行历史缓冲区。

## 4. 用“把杯子放进柜子”完整走一遍

我们先不讲网络结构，只看人是怎样理解一段长动作的。

### 4.1 最初几步

机器人开始向杯子移动：

```text
机械臂向右移动
机械臂向前移动
夹爪仍然张开
```

此时只能比较确定地说：

> 机械臂正在靠近杯子。

还不能确定它最终想：

- 把杯子放进柜子；
- 把杯子放到托盘；
- 把杯子递给另一只手；
- 只是碰一下杯子。

### 4.2 夹爪闭合

接下来：

```text
夹爪靠近杯子
夹爪闭合
杯子开始跟随机械臂移动
```

现在可以判断：

> “抓住杯子”这个子目标大概率已经完成。

但最终目的仍然可能不唯一。

### 4.3 开始向柜子移动

接下来：

```text
机器人抬高杯子
绕开桌面障碍
持续向柜门方向移动
```

现在“把杯子放进柜子”的可能性开始高于“放到托盘”。

### 4.4 杯子进入柜内并被释放

最后：

```text
杯子进入柜子内部
夹爪张开
杯子留在柜内
机械臂退出
```

现在可以比较可靠地输出：

```yaml
已经达成:
  - Inside(cup, cabinet)

动作的功能:
  - 将杯子从桌面转移到柜内

与总任务的关系:
  - 直接完成核心目标
```

### 4.5 人类理解长动作时实际做了什么

人脑没有简单地把所有手部位移相加，而是：

1. 保留动作先后顺序；
2. 观察手和物体是否发生接触；
3. 判断物体是否跟着手移动；
4. 把局部变化概括成“抓住”“搬运”“释放”；
5. 再把这些事件组合成“把杯子放进柜子”。

模型也应该学习类似的分层过程。

## 5. 我认为“长动作理解”至少包含三层

“看得更长”本身并不等于“理解得更深”。<br>
我认为需要同时处理下面三层。

### 5.1 第一层：时间上看见更长历史

模型需要获得多个已经执行的 action chunk，而不是只看当前一个。

```text
chunk 1
chunk 2
chunk 3
...
chunk N
```

这是“记得更久”。

### 5.2 第二层：把数字动作概括成事件

连续动作通常只是一串数字：

```text
dx, dy, dz, rotation, gripper
```

模型需要从数字变化中识别：

```text
接近物体
闭合夹爪
建立接触
物体被抬起
物体被搬运
物体被释放
```

这是“知道发生了什么”。

### 5.3 第三层：理解事件为什么有用

同一个“抓起杯子”可以服务不同目标：

```text
抓起杯子，以便放进柜子
抓起杯子，以便放到托盘
抓起杯子，以便交给另一只手
```

模型还需要把当前子目标放进完整任务中，判断它的功能。

这是“知道为什么做”。

因此：

```text
较长动作理解
≠ 单纯增加输入步数

较长动作理解
= 长历史记忆
  + 局部事件抽象
  + 目标/功能推断
  + 对不确定性的正确表达
```

## 6. 初步模型结构：三级时间层次

我目前最倾向的结构是：

```text
已执行的原始动作
      ↓
第一级：局部 Action Encoder
      ↓
每个短 chunk 的内部表示
      ↓
第二级：事件聚合
      ↓
接近 / 抓取 / 抬升 / 搬运 / 释放
      ↓
第三级：因果时间聚合器
      ↓
子目标 + 功能性意图 + 置信度
```

下面逐层解释。

### 6.1 第一级：局部 Action Encoder

Encoder 可以理解为“翻译器”。

它把一个短 action chunk 的原始数字，翻译成模型内部较容易使用的一串特征。

输入可以包括：

```yaml
动作:
  - 末端位置变化
  - 末端旋转变化
  - 夹爪开合

上下文:
  - chunk 开始时的画面
  - chunk 结束时的画面
  - 机器人自身状态
```

输出暂时不必是自然语言，可以只是一个内部向量：

```text
chunk_1 → action token 1
chunk_2 → action token 2
chunk_3 → action token 3
```

这里的 **token** 可以先简单理解为：

> 模型对一个短片段形成的内部摘要卡片。

### 6.2 第二级：事件聚合

多个相邻 chunk 可能共同组成一个事件。

例如：

```text
向杯子移动
→ 微调夹爪
→ 闭合夹爪
→ 杯子被抬起
```

合起来才是：

```text
Grasp(cup)
```

事件边界可以参考：

- 夹爪从张开变成闭合；
- 新的接触产生；
- 物体开始与机械臂共同移动；
- 物体不再与机械臂共同移动；
- 柜门角度越过“打开”阈值；
- 某个状态连续一段时间保持成立。

“连续保持成立”很重要。

例如夹爪闭合的一瞬间碰到了杯子，但下一帧杯子就滑走了，这不能算稳定抓取成功。

### 6.3 第三级：因果时间聚合器

时间聚合器负责阅读多个 action token 或 event token。

“因果”表示：

> 判断当前意图时只能使用已经发生的历史，不能偷看未来动作。

它可以采用 causal Transformer。

Transformer 可以先理解成：

> 一种擅长阅读长序列，并判断序列中哪些部分彼此相关的神经网络。

输入：

```text
Open(cabinet)
→ Approach(cup)
→ Grasp(cup)
→ Lift(cup)
→ MoveTowards(cabinet)
```

输出：

```yaml
achieved_subgoal:
  predicate: Grasped
  object: cup

functional_intent:
  relation: enables
  downstream_goal: Inside(cup, cabinet)

confidence: 0.82
```

这里的 `confidence` 表示模型有多确定。

## 7. 模型需要一份“执行记忆”

可以给系统维护一个不断更新的历史缓冲区：

```yaml
history:
  - observation_before_chunk
  - executed_action_chunk
  - observation_after_chunk
  - robot_state
  - detected_contacts
  - gripper_change
  - timestamp
```

每执行完一小段，就向历史末尾增加一条记录。

### 7.1 历史会不会无限变长

不会一直原样保存全部信息，否则计算越来越贵。

可以采用分层压缩：

```text
最近 2 秒：
保留详细动作

最近 10 秒：
压缩成 chunk token

更早历史：
压缩成 event token / 已达成子目标
```

类似人类记忆：

- 刚发生的事情记得很细；
- 较早的事情记成“我已经打开柜门”；
- 不需要永久记住每一毫米的手部运动。

### 7.2 压缩时不能丢掉什么

至少需要保留：

- 事件先后顺序；
- 抓取/释放等关键夹爪变化；
- 接触对象；
- 物体关系变化；
- 已经稳定达成的子目标；
- 当前仍然可能的意图候选。

## 8. 累计变化到底有没有用

结论是：

> **有用，但只能做辅助特征或对照实验，不能独自代表较长动作的含义。**

### 8.1 什么是累计变化

例如机械臂在一段时间内：

```text
x 总共移动 +20 cm
y 总共移动 -5 cm
z 总共移动 +10 cm
夹爪从开变关
```

可以把起点和终点的差记为：

```text
endpoint delta
```

这里的 delta 就是“变化量”。

### 8.2 为什么累计变化不够

#### 它会丢失动作顺序

```text
动作 A：先闭合夹爪，再向上移动
动作 B：先向上移动，再闭合夹爪
```

两者最终的手部位置和夹爪状态可能相同。

但：

- A 可能抓住并抬起了杯子；
- B 可能先从杯子旁边抬走，再在空中闭合夹爪。

#### 它会丢失中途接触

同样从位置 A 移动到位置 B：

- 路径 1 可能推倒一个物体；
- 路径 2 可能绕开物体；
- 最终位移完全相同。

#### 相同位移可以服务不同任务

机械臂都向右移动 20 cm：

- 一次是在把杯子送入柜子；
- 一次是在把托盘拖到桌边；
- 单凭位移无法判断功能。

### 8.3 累计变化适合怎样使用

建议把它放在实验中比较：

| 输入方式 | 保留什么 | 丢失什么 |
|---|---|---|
| 只用 endpoint delta | 起点到终点的总体变化 | 顺序、接触、路径 |
| 有序 action sequence | 详细顺序和动作过程 | 计算较多 |
| event sequence | 语义事件和顺序 | 部分细节 |
| sequence + delta | 过程加总体变化 | 成本稍高 |

如果“有序序列 + 事件”明显优于“只有累计 delta”，就能证明较长动作理解不能被简单位移替代。

## 9. 不能逼模型过早猜出唯一意图

### 9.1 共享动作前缀

下面两个任务的前半段可能完全相同：

```text
任务 A：抓起杯子 → 放进柜子
任务 B：抓起杯子 → 放到托盘
```

在“抓起杯子”之后，模型可能只能确认：

```text
已达成子目标：Grasped(cup)
```

但不能确认最终目标。

### 9.2 应该输出候选和概率

模型可以先输出：

```yaml
intent_status: ambiguous

candidates:
  Inside(cup, cabinet): 0.50
  On(cup, tray): 0.50
```

当机械臂开始向柜子移动：

```yaml
candidates:
  Inside(cup, cabinet): 0.82
  On(cup, tray): 0.18
```

杯子进入柜子后：

```yaml
candidates:
  Inside(cup, cabinet): 0.99
  On(cup, tray): 0.01
```

### 9.3 意图显现时刻

可以定义一个时间点 \(t^\*\)：

> 到哪个时刻为止，已经发生的动作才足以区分真正意图？

这是一个比“整条轨迹最后猜对没有”更有意思的指标。

好的模型应该：

- 证据不足时保持不确定；
- 关键动作出现后及时更新；
- 不应该在最初几步就自信地乱猜。

## 10. 数据怎样自动构造

第一阶段建议使用 LIBERO 仿真环境。

仿真环境的优势是：

- 能知道机器人和物体的精确状态；
- 能重放专家轨迹；
- 能检查杯子是否真的在柜子里；
- 能自动生成较可靠的结构化标签。

### 10.1 每一帧需要记录什么

```yaml
time:
rgb_images:
robot_state:
executed_action:
gripper_state:
contacts:
object_states:
predicates:
```

其中 predicate 是“可以判断真假的状态”，例如：

```text
Grasped(robot, cup)
Open(cabinet)
Inside(cup, cabinet)
On(cup, tray)
```

### 10.2 从轨迹中找稳定事件

例如：

```text
第 100 帧：夹爪碰到杯子
第 101 帧：杯子轻微移动
第 102 帧：杯子滑落
```

不能标为“抓取成功”。

另一个例子：

```text
第 100 帧：夹爪闭合
第 101–120 帧：杯子持续跟随机械臂
第 121 帧：杯子被抬离桌面
```

可以比较可靠地标为：

```text
Grasped(cup)
```

### 10.3 同时生成不同长度的窗口

对同一条轨迹，可以截取：

```text
8 步窗口
16 步窗口
32 步窗口
64 步窗口
一个完整事件窗口
从任务开始到当前的累计历史
```

这样可以观察：

> 模型需要看多长的动作，才能从“局部运动”进展到“子目标”和“功能意图”。

### 10.4 标签分成不同层级

```yaml
L1_action_description:
  - close gripper near cup

L2_achieved_subgoal:
  - Grasped(cup)

L3_functional_intent:
  achieved: Grasped(cup)
  relation: enables
  downstream_goal: Inside(cup, cabinet)

L4_final_task:
  - Put cup inside cabinet
```

初期应先做好 L2，因为它最容易自动验证。<br>
等 L2 标签可靠后，再增加更难的 L3 功能性意图。

## 11. 第一版模型不必直接使用 π0.5

### 11.1 为什么

π0.5 很大，训练和调试成本高。

如果数据中根本没有足够的动作信息，那么直接改 π0.5 会浪费大量时间。

所以建议分三版做。

### 11.2 V0：固定窗口的小模型

目的：

> 先验证动作是否真的能提供额外目标信息。

模型可以很简单：

```text
动作序列 → 小型时序编码器 → 子目标分类
```

比较：

```text
视觉 + 状态
视觉 + 状态 + 动作
```

如果加动作完全没有提升，应先检查数据设计。

### 11.3 V1：事件化长历史模型

在 V0 有信号后，加入：

- 事件分段；
- event token；
- 多尺度历史；
- 意图候选分布；
- 意图显现时刻。

这一版专门回答“怎样理解较长动作”。

### 11.4 V2：接入 π0.5

最后才把 observed-action encoder 和理解头接到 π0.5 的共享表示。

```text
图像 / 状态 ─────────────────┐
                              ↓
已执行动作 → action encoder → 共享层
                              ├→ 动作控制
                              └→ 子目标/功能意图
```

这样才能研究：

> 学习较长动作的目标含义，是否会反过来改善机器人控制？

## 12. 训练时怎样防止模型作弊

### 12.1 不能给原始任务指令

如果输入里有：

```text
“把杯子放进柜子”
```

输出再预测：

```text
“目的是把杯子放进柜子”
```

模型只是在复述答案，并没有从动作理解意图。

严格诊断模式应屏蔽原任务指令。

### 12.2 不能看未来动作

如果我们判断“抓杯子”阶段的意图，却让模型看到后面“向柜子移动”的动作，也是在偷看答案。

所以 causal mask 必须保证：

```text
当前判断只能看当前时刻以前的动作
```

### 12.3 不能把仿真真值直接当输入

仿真器可以直接告诉我们：

```text
Inside(cup, cabinet) = True
```

它适合作为训练答案，却不能作为正式模型输入。<br>
否则相当于把标准答案放在试卷旁边。

## 13. 怎样证明模型真的使用了长动作

至少需要以下对照。

### 13.1 视觉和状态基线

```text
输入：视觉 + 状态
```

它告诉我们：

> 不看动作，只看画面已经能猜多准？

### 13.2 真实动作

```text
输入：视觉 + 状态 + 真实有序动作
```

如果它明显优于视觉和状态基线，动作才可能提供了额外信息。

### 13.3 打乱动作

```text
输入：视觉 + 状态 + shuffled actions
```

也就是把动作顺序随机打乱。

如果打乱后完全不变，说明模型可能没有使用动作顺序。

### 13.4 反转动作

```text
输入：视觉 + 状态 + reversed actions
```

例如把：

```text
靠近 → 抓住 → 抬起
```

改成：

```text
抬起 → 抓住 → 靠近
```

如果模型仍认为两者含义相同，就没有真正理解时序结构。

### 13.5 错任务动作

保持视觉相同，把动作替换成另一个目标的动作。

例如当前场景相同：

- 正确动作向柜子移动；
- 错配动作向托盘移动。

模型的意图预测应该发生变化。

### 13.6 相同累计变化、不同过程

专门构造：

```text
最终位置相同
累计 delta 相同
动作顺序或接触过程不同
```

如果有序动作模型能区分，而 delta-only 模型不能，就能直接回答师哥关于“累计变化是否足够”的问题。

---

## 14. 需要画出的四条关键曲线

### 14.1 窗口长度与子目标准确率

```text
横轴：看了多少步动作
纵轴：子目标预测准确率
```

看更长历史后，准确率是否提高？

### 14.2 窗口长度与动作额外贡献

比较：

```text
Score(视觉 + 状态 + 动作)
-
Score(视觉 + 状态)
```

这个差值可以记作 \(\Delta_A\)。

它的中文意思是：

> 加入动作以后，模型究竟额外提高了多少？

### 14.3 窗口长度与歧义率

随着动作越来越长：

- 可行意图候选是否逐渐减少；
- 模型是否在正确时间变得更确定。

### 14.4 模型预测的意图显现时间

比较：

```text
真实需要看到的关键证据时刻 t*
模型开始确定的时刻 预测t*
```

模型太早确定，表示它可能在猜；太晚确定，表示它没有及时利用动作证据。

## 15. 一个最小可行 PoC

PoC 是 Proof of Concept，即“概念验证”。

它不追求一次做出完整论文，只验证核心想法有没有信号。

### 第一步：选择少量任务

从 LIBERO-Goal 选择 4–8 个任务：

- 场景相似；
- 最终目标不同；
- 有明显抓取、放置或开关事件；
- 最好存在共享动作前缀。

### 第二步：生成 L2 子目标标签

先实现少量谓词：

```text
Grasped
Open
Closed
Inside
On
```

回放轨迹并检查这些谓词何时稳定成立。

### 第三步：训练四个小模型

```text
模型 A：视觉 + 状态
模型 B：动作 only
模型 C：视觉 + 状态 + 有序动作
模型 D：视觉 + 状态 + 打乱动作
```

### 第四步：比较不同窗口

```text
8 / 16 / 32 / 64 步
固定窗口
事件窗口
```

### 第五步：做 delta 对照

```text
endpoint delta
有序 action sequence
event sequence
sequence + delta
```

### 第六步：决定是否继续

继续进入大模型的最低信号：

1. 真实动作明显优于视觉+状态；
2. 真实动作明显优于打乱动作；
3. 有序序列在关键样本上优于累计 delta；
4. 更长窗口确实带来更高层语义，而不只是终态画面泄漏。

如果这四项都没有出现，就不应立即修改 π0.5。

## 16. 和参考论文的关系

这份初步方案不是凭空产生的。

### π0 / π0.5

给出短 action chunk 的控制骨干。<br>
我们的方案不改变其短时闭环优势，而是在旁边增加已执行动作历史。

### LingBot-VA

说明视频和动作可以放进因果历史，使用过去信息和缓存维持长时记忆。<br>
但它主要理解视觉动力学，我们还要增加结构化子目标和功能意图。

### VLA-JEPA

提醒未来信息只能作为训练答案，不能进入当前预测输入。<br>
这直接影响我们的 causal mask。

### Fast-WAM

说明辅助任务的主要价值可能发生在训练时，测试时可以移除辅助生成分支。<br>
未来 A2FI 也可以训练时存在、正式控制时关闭输出头。

### LACY / Anchor-Align

说明动作—语言双向或低层语言—动作对齐已经有人做。<br>
所以我们必须研究：

- 更长的动作窗口；
- 子目标/功能层级；
- 共享前缀歧义；
- 动作条件贡献。

## 17. 目前比较确定与尚未确定的部分

### 17.1 我目前比较确定的判断

1. 不应该为了理解长动作而强迫策略输出超长 chunk；
2. 理解分支应聚合已经真实执行的多个 chunk；
3. 原始动作顺序必须保留；
4. 累计 delta 只能作为辅助或对照；
5. 事件层是连接低层数字和高层意图的关键中间层；
6. 证据不足时必须允许输出多个候选意图；
7. 第一阶段应先验证动作是否有额外信息，再改 π0.5。

### 17.2 仍需实验决定的设计

1. 固定窗口和事件窗口，哪个更稳定；
2. event boundary 用规则、模型还是二者结合；
3. 最近多少步保留原始动作，较早历史何时压缩；
4. action encoder 用 MLP、1D Conv 还是小型 Transformer；
5. L3 功能关系能否可靠自动生成；
6. 意图候选的真值怎样标注；
7. 理解分支是否需要在控制推理时一直运行；
8. shared-A2FI 是否真的比低层动作描述更能改善控制。

## 18. 需要和师哥确认的问题

1. “较长动作理解”的第一目标，是识别子目标还是直接预测功能性意图？
2. 是否同意保留短 action chunk，只给理解分支维护长历史？
3. 是否同意先用 LIBERO 小模型验证，再接 π0.5？
4. 第一版事件类型是否只做“接近、抓取、搬运、释放、打开、关闭”？
5. 累计 delta 是否定位为 baseline/辅助特征，而不是核心表示？
6. 共享前缀歧义是否作为主要研究问题？
7. 主实验是否同意屏蔽原始任务指令和未来动作？
8. 如果动作在视觉/状态之外没有额外信息，是否接受转向数据/诊断 benchmark？

## 19. 最后再用一个比喻总结

把一段机器人动作想成一篇文章：

```text
每个连续动作数字      ≈ 字母
每个 action chunk     ≈ 一个短词
抓取/搬运/释放事件     ≈ 一个句子
子目标                ≈ 一段话
功能性意图            ≈ 这段话在整篇文章中的作用
```

只把所有字母的位移加起来，不能理解文章意思。

模型需要：

1. 记住词的先后顺序；
2. 把词组合成句子；
3. 把句子组合成段落；
4. 判断段落在全文中的作用；
5. 在文章还没写完时承认“现在还不能确定结局”。

因此，这个问题目前最完整的一句话答案是：

> **让模型理解较长动作，不是让它一次生成更长的控制序列，也不是只计算起点到终点的累计变化；而是让它因果地保存真实执行历史，把短 chunk 分层聚合为事件和稳定子目标，并随着新动作证据不断更新对功能性意图的判断。**
